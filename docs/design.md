# Modal — Design

Oct 14, 2026 · @Neil Durant

This document specifies behaviour and architecture, including agreed future behaviour and clearly marked proposals. Implementation order, progress and the someday maybe list live only in [schedule.md](schedule.md). [grammar.md](grammar.md) is the reference for implemented keys, [configuration.md](configuration.md) for configuration, [decisions.md](decisions.md) for dated reasoning, and [status.md](status.md) for the current handoff and validation evidence.

## Overview

A fast, keyboard-driven MIDI sequencer for Windows and Linux: what Voyetra Sequencer Plus Gold might have been if it were designed in 2026. It is not a clone. It keeps SPG's goals (speed, precision, every action a keystroke away) and borrows its editing model from Vim, Emacs and Mutt.

It is a GUI application drawn on a fixed character grid, like a terminal but without a terminal's limits. It is MIDI-only: it records, edits and plays MIDI to hardware and to software synths, and leaves audio to other tools. Working title: Modal, after both modal editing and musical modes.

## Design principles

1. **Keyboard first, keyboard complete.** Every action is reachable from the keyboard. The mouse is optional and never required.
2. **The cursor is always exact.** It sits on one cell, one event, one tick. Nothing is ever ambiguously selected.
3. **A grammar, not a list of shortcuts.** Counts, operators, motions and objects compose, so users can do things nobody designed a feature for.
4. **Timing is sacred.** The playback and recording engine never waits on the UI, the disk or the renderer.
5. **Fast to start, fast to respond.** Launch in under a second; every keystroke redraws within one frame.
6. **Plain text where possible.** Songs, configuration and keymaps are human-readable and diffable.
7. **Show the data honestly.** The event list shows the stored events faithfully. Playback-only track settings are visible wherever they affect how a track sounds.
8. **Small and owned.** Few dependencies, a codebase one person can understand end to end.

## Scope

Version 1 is a complete, reliable sequencer for one person recording and editing MIDI. Everything else waits until that core feels right in daily use.

## Data model

A song is a list of tracks, each holding a time-ordered list of events, with all times in 64-bit integer ticks at a fixed 960 PPQN. Files at other resolutions are converted on import. Notes are stored as single events with a duration, not as separate note-on/note-off pairs, which makes editing simpler and avoids stuck notes.

**Keeping resolution changeable.** 960 is the starting value, but nothing should depend on it:

- PPQN is one named constant; no literal tick values (480, 240, …) appear anywhere else in the code.
- Musical lengths (grid steps, step-entry durations, quantise values, keymap and config settings) are stored as fractions of a whole note, e.g. 1/16 or 1/8 triplet, and converted to ticks only at the point of use.
- Song files record their PPQN; loading a file at a different resolution rescales it, exactly as SMF import does.
- Display of bar:beat:tick derives its tick-field width from PPQN.
- Unit tests run at more than one resolution (e.g. 960 and 6720) to catch hidden assumptions.
- The constant (`kPpqn`) is the resolution of new songs and the target of import. Every conversion takes the PPQN from the song rather than the constant, so the same code runs at any resolution in tests (decided in milestone 1).

**Tempo.** Tempo is stored as integer microseconds per quarter note, which round-trips SMF exactly, and shown as BPM. The accepted range is 1 to 1000 BPM; SMF tempos outside it are clamped on import. Tempo changes are steps (no ramps). Tick-to-time conversion splits each calculation into whole quarter notes plus remaining ticks, so no intermediate value overflows for centuries of song time, without 128-bit arithmetic. A tick's time is the first whole nanosecond not before it, and a time's tick is the last tick at or before it, so converting a tick to time and back always gives the same tick.

**Sections and labels (decided October 2026)**

Two distinct ideas:

- **Sections are the song's structure.** A song is an ordered sequence of named sections (Intro, Verse 1, Chorus, Bridge…) that together cover the whole timeline, with no gaps or overlaps, each spanning every track. A new song starts as one section covering everything ("Section 1"), split as the structure emerges.
- **Labels are bookmarks:** named points for navigation and reminders ("fix this fill"), with no structural meaning. Vim's marks (`ma`, `'a`) are in the same family. Called markers until November 2026, when they were renamed labels (decided then) so they and marks aren't confused, with the play-from marker the only marker left: the commands, keys (`]l` / `[l`), event list rows, theme role and song file lines say label, songs and themes saved with `marker` still loading. A MIDI file's marker meta events are still markers, imported as labels. The dated entries in decisions.md, and the milestones' records, still say markers, as they were then. With the rename, `:label NAME` puts a label at the cursor's time, or renames the one there, asking for the name when given none, with the one there to edit; `:label-delete` deletes the one there, or every one in a selection, as one undo step. Before them, labels were made and deleted in the conductor's event list alone, which was hard to find, reached only by `gt` / `gT` past the tracks; so (decided November 2026) `gc` shows the conductor's list from any view, at the cursor's time, and the palette's `#` lists the conductor first, as "Conductor" with "track 0, the tempos, meters, sections and labels" beside it.

Section properties: a name, a length, an optional colour (from the theme's section palette), its takes (see Input and recording), its cue slot (see Playback and recording behaviour), and later a link to another section and alternatives.

- **Content is stored per section.** Each section holds the conductor's tempo and meter changes, its labels, and each track's meter and events, all positioned relative to the section's start. Moving or duplicating a section then changes nothing inside it, and the song file is grouped by section.
- **A flattened timeline.** From the sections the core builds each song snapshot's flattened form: absolute events, meters and tempo per track, as before sections. Playback planning, the scheduler, recording, SMF import and export and the views read the flattened form, so they work on one timeline as they always have; edits go to the section concerned.
- **Events belong to the section they start in.** A note sustaining past the section's end still belongs to the section it starts in, and moves with it whole.
- **Bar lines realign at every section boundary.** Each section starts with a new bar on every track, whatever the meters, so a bar on a track in another meter can never straddle two sections. Bar numbers still run on through the song in the usual way (Verse 1 is bars 5–20 after a 4-bar Intro). A boundary that would fall mid-bar on some track splits that bar: its first part becomes a remainder bar, a real bar with a meter change of its own (a 7/8 bar cut after one eighth becomes a 1/8 bar), and the original meter carries on in the next section. Making such a boundary warns, naming the tracks, e.g. "splits bar 5 of Lead (7/8)", since a boundary that doesn't line up is usually not a real section boundary. So every section is a whole number of bars on every track. The remainder always fits a time signature, since a boundary is always at some track's bar line.
- **Tempo and meter changes belong to their section** and move with it.
- **A section's length** is stored in ticks, and is a whole number of the conductor's bars, counted through its meter changes.
- **Each section has its own tempo and meter at its start (decided in milestone 4),** even where they repeat the section before, so a section moved elsewhere keeps its tempo: a 140 BPM chorus moved after a 90 BPM verse stays at 140. The flattened tempo map leaves out repeats.
- **The end of the song (decided in milestone 4).** A new song is one section, "Section 1", of eight bars. It was "Song" at first, which read as if it were the song itself rather than a section waiting to be named; "Section 1" says it's a section, one of more to come, as "Track 1" does for tracks (decided in milestone 4). Anything put past the end (a recording, an edit, a marker, a tempo or meter change) grows the last section to the next bar line; it never shrinks by itself. Changing the conductor's meter keeps every section's length in ticks, ending it in a remainder bar if need be, except the last, which grows to the next bar line instead. Splitting a section mid-bar does the same for the new section, which starts a new bar: it ends in a remainder bar, or grows if it's the last.
- **How the remainder bars are stored (decided in milestone 4).** The conductor's meter in a section is kept a whole number of bars explicitly, so a remainder bar is written into it as a meter change, and the file can give the length as `bars=N`. A track's own meter needn't end on the section's end: the end cuts its last bar short, and flattening makes that a remainder bar, so a section growing restores the whole bar. Splitting a section writes the remainder into both.
- **In the core (decided in milestone 4).** `Track` holds only settings; sections hold each track's content (`TrackContent`: an optional meter of its own and its events). The song keeps its flattened timeline (the tempo, the conductor's meter, each track's meter and events), rebuilt after each edit and shared between snapshots, which playback, export, the views and the tools read. Edits in ticks from the song's start (`updateEvents`, `updateMeter`, `updateTempo`, `setMarker`) are shared out to the sections by where things start, so the recorder and SMF import work as before; operators on sections come later.
- **Labels belong to the section they're in,** and move and are copied with it. A label's name is unique within its section, and it is named with its section where that matters, e.g. "Chorus (2) › fix this fill", so duplicating a section never needs its labels renamed. Section names are unique across the song: a duplicated section is numbered, so a copy of "Chorus" is "Chorus (2)", then "Chorus (3)". Numbers added to make a name unique, of sections and labels alike, go in brackets, as Windows numbers copies of a file (decided October 2026, rather than "Chorus 2", which could be taken for the second chorus of the song, and gave "Section 1 2" for a copy of "Section 1").

**Per-track meters (polymeter)**

As in SPG, each track has its own sequence of bars and time signatures, so tracks can run different meters at the same moment (4/4 against 3/4, 7/8 against 4/4) for polyrhythmic writing.

- **Time is shared; bars are not.** All events sit on one timeline in ticks, and tempo is global. Bars are a per-track view of that timeline, so "bar 10" on a 3/4 track is earlier than bar 10 on a 4/4 track.
- **The conductor track (decided October 2026).** The song's tempo and reference meter are a special track, the conductor, which holds only tempo and meter changes (per section), never notes, like the tempo track of other sequencers. Labels, the loop range, the metronome and the main position display are measured against its bars, so deleting, reordering or muting tracks never changes the song's bars. SMF export writes its meter as the file's time signatures, since standard MIDI files have only one. An empty song has bars and a tempo before it has any tracks.
- **Tracks follow the conductor's meter unless they have their own.** In each section, a track either follows the conductor's meter or has its own, and then its whole meter in that section is its own; it never follows for part of a section. A track following the conductor changes with it; a track with its own meter keeps it, even if it happens to match. `:meter follow` sets a track following again. Meter commands change the conductor and the tracks following it by default, and in a selection only the tracks selected.
- **Positions are always relative to a track.** The cursor's position and the inspector use the bars of the track the cursor is on. Typed positions like `:goto 10` or `10G` use the current track's bars; `:goto ref 10` uses the conductor's.
- **Motions follow each track's bars.** `}` moves to the same position in the next bar of the current track. Operators that span several tracks, such as a Visual block in the arrangement, select a time range, which may start or end mid-bar on some tracks.
- **Copy and paste by time.** Pasting from a 3/4 track into a 4/4 track keeps the material's timing, not its bar positions.
- **Apply meter to a range.** In the arrangement, select a range and set a time signature (`:meter 3/4`, or from the leader menu). Bars are rebuilt from the range start; if the range doesn't divide evenly, the last bar becomes a shorter remainder bar, e.g. 10 beats in 3/4 gives three 3/4 bars and one 1/4 bar.
- **Beats and remainder bars (decided in milestone 1).** The beat is the denominator note, so 6/8 counts six eighth-note beats. A meter set mid-bar ends that bar with a remainder bar of the exact leftover, using a finer denominator when the leftover isn't whole beats (half a beat into a 4/4 bar gives a 1/8 bar); a leftover no time signature can express, such as a single tick, moves the change on to the next beat. A change inside the first bar after another change replaces that bar's meter rather than adding a bar. Removing a change keeps later changes at their positions in time, adding remainder bars where needed, and repeating the meter already in effect adds nothing.
- **Unify meters.** `:meter unify` sets the selected tracks (or all tracks) following the conductor, removing polymeter where it isn't wanted; from a track with its own meter, `:meter unify` can also copy that meter to the conductor, for a song whose real meter is that track's.
- **Arrangement drawing.** Columns represent time, not bars (decided: SPG's bar-aligned view made polymeter confusing). Each track draws its own bar lines, so tracks in different meters show bar lines at different places, and the ruler shows the conductor's bars.

**Selections across tracks in different meters**

- **Bar motions use the cursor's track.** In a Visual selection, `}` and `{` step by the bars of the track the cursor is on. Start on the 4/4 track and the selection grows in 4/4 bars, even across a 3/4 track; move the cursor onto the 3/4 track with `j` and it grows in 3/4 bars. This is the same rule as everywhere else, so nothing special to learn.
- **A motion for any bar line.** `]|` and `[|` move to the next or previous bar line on any track in the selection, for selecting exactly up to where the meters next coincide or diverge.
- **Partial bars are shown.** Where a selection edge falls mid-bar on a track, that edge is drawn half-shaded, so it's clear the track is only partly selected.
- **Operators act on the time range.** Transforms, copy, delete and quantise work on whatever falls inside it, whole bars or not. Operations that need whole bars, such as applying a meter, use the bars of the cursor's track.

* **Song:** title, PPQN, tracks, sections, global settings such as count-in and metronome.
* **Section:** name, length, colour, the conductor's tempo and meter changes, labels, and each track's content: its own meter (or none, following the conductor) and its events, all relative to the section's start. Later its takes and cue slot.
* **Track:** a stable ID, name, output port, MIDI channel, mute/solo/arm, note chasing on/off, optional transpose, velocity offset and time offset applied at playback, grid and default note length (see Editing grammar). Its meter and events are held by the sections. The ID survives edits, so the engine can follow a track from one song snapshot to the next.
* **Event:** tick, type, and type-specific fields. A note has pitch, velocity, duration and release velocity. Other types are CC, program change, pitch bend, channel and poly aftertouch, SysEx and meta (text, markers). Events carry no channel; the track's channel applies.
* **Event order.** A track's events are in tick order, and events at the same tick are sent in the order stored. Import and editing put non-note events (program change, CC, etc.) before notes at the same tick, so a program change at 1:1:0 always takes effect before the first note.
* **Overlapping notes.** The model allows overlapping notes of the same pitch, since imported files can contain them; the editor never creates them (see Playback and recording behaviour).
* **Labels** (once markers): bookmarks, named positions used as motion targets (see Sections and labels).
* **Patterns (later):** reusable phrases referenced from the arrangement, if a pattern-based workflow proves useful.

The model is immutable at the edit level: each edit produces a new song state, sharing unchanged sections and tracks. That makes undo cheap and lets the engine read a consistent snapshot while the UI edits the next one.

## Editing grammar

Editing follows Vim's model: `[count] operator [count] range-or-object`, with `.` to repeat the last change. Every key, what it takes and where, is in [grammar.md](grammar.md), which describes the grammar as it is; how each part was decided, with the dates and the reasons, is in [decisions.md](decisions.md), under the same headings.

**Principles (decided over milestones 4 to 6, made consistent in November 2026).**

- **A range or object says what it takes.** A range runs from the cursor to a boundary its key names (`]b`, `]s`, `]l`, `gg`, `G`, marks, finds, matches); an object is a whole thing at the cursor named by its letter (`ib`, `ab`, `in`, `ic`, `is`, `as`, `it`, `ie`, `gn`). A letter means the same in every form: `b` is a bar in `]b` and `ib`, `s` a section in `]s` and `is`. Keys that only move (`Tab`, `(`, `)`) say so after an operator.
- **An object never reaches beyond the cursor's place:** on a track, that track; on the section strip, every track. So the strip is for the song's arrangement and the tracks for a track's work, and an operator means the same with an object wherever both are offered.
- **Selecting first is looking first:** an object in Visual mode selects exactly what an operator would take with it, so `vXd` is always `dX`, which a test checks for every object and count in every view.
- **Contents or time.** `i` objects and `d` leave silence; `ab`, `D` and `P` take time out or put it in, rippling only within the section, so the rest of the song stays aligned. Changing the song's length is explicit (`, b d`, `, b i`, the strip).
- **One command per meaning.** A command does one thing, named for it; keys are bound to several commands, each doing something in places of its own, and mean the one that does something where the cursor is. The palette and the keys list name each as itself, and say what it does in the view the cursor is in.
- **The key decides, not the history.** What `p` does is decided by the key and where the cursor is, never by how the register was filled; what a macro does when a command fails is decided by the command's outcome, never by its message.
- **Toggles say their state (decided November 2026, after use).** In the hint menu a toggle shows its name and what it's set to now, `Quantise marks: shown`, rather than what it does, as its state was otherwise only seen by trying it.
- **Taught as it's used.** The hint menu after any key that starts longer ones, and after an operator (objects and motions apart, each with what it would take here); `, ?` for every key here; keys waiting for a letter saying what they want; the status line saying what an operator will do and what was done.
- **Lines typed into are safe:** Escape gives one up; Backspace on an empty line does nothing; a question takes only its own answers.

**Proposed editing behaviour.** These notes describe the intended interactions, not a backlog or implementation status. Work assignments are in schedule.md; implemented bindings are in grammar.md.

- **Insert mode and step entry**, with `c` as change (delete the range and start step entry there, `cib`) and `Ctrl-Space` as its leader.
- **Scale lock** (`, T s` proposed), `k` / `j` then moving by scale steps, with a semitone motion that ignores it (key to decide); following a key's scale waits for a key or chord track.
- **Moving in pitch:** `gk` / `gj` to the next note above or below sounding at the cursor's time, and `gp` and a pitch to go straight to it (proposed).
- **Default note length from the leader,** `, l` and keys (`, l 8 t` for 1/8T) (proposed).
- **Sections:** recolouring (`, s c`), `:section length N`.
- **Track command grouping:** `, t` groups track management; actual commands and bindings are listed in grammar.md.
- **Search:** across tracks in the arrangement, drum-map names (`/kick`), matching controllers highlighted in the lane, interval and rhythm patterns.
- **Ripple to the end of a track** (`:ripple track`), for rare cases.
- **Undo:** an undo tree; Vim's other registers (`"0`, `"_`, `"+`).
- **A jump list (requested November 2026):** `Ctrl-o` and `Ctrl-i` go back and forward through the places jumped from and to, as in Vim, across views: jump to the bridge to check something, and `Ctrl-o` goes straight back to where editing was. Which moves count as jumps (marks, `gg`/`G`, sections, search, opening another view) is to decide, as is how it sits with `` ` `` / `'`, which already go back to before the last jump.
- **Paste history (requested November 2026):** as Emacs's kill ring and yank-pop: straight after a put, one key replaces what was put with the copy before, and again with the one before that, so a phrase copied a few moves ago isn't lost. Vim's numbered registers (`"1` to `"9`) are the same history by name; the key, how far back it goes, and whether deletes go into it as well as yanks are to decide.
- **Visual mode:** `:select pitch C1 in section` and drum-map names; hand-picked notes and pitch rows apart, with folding.

## MIDI transforms

SPG-style transforms are first-class operators: each applies to any motion, object or selection, takes parameters on the command line, and is reachable from the `, x` leader menu. Each is a pure function on a list of events, so it is easy to test.

| Transform | What it does |
| --- | --- |
| Transpose (chromatic) | Shift pitches by semitones or octaves |
| Transpose in key | Move notes by scale degrees, staying in the song's key and scale |
| Invert | Mirror pitches around a pivot note, chromatically or within the scale |
| Retrograde | Reverse the time order of notes in the range |
| Velocity compress / expand | Scale velocities towards or away from a centre value |
| Velocity scale, offset, limit | Multiply by %, add or subtract, clamp to a min/max |
| Velocity ramp | Crescendo or diminuendo across the range |
| Time stretch | Double time, half time, or any ratio, about the range start |
| Quantise | Grid, strength %, swing, start only or start and length |
| Humanise | Small random changes to time and velocity, within set limits |
| Length | Legato (extend to next note), fixed length, scale lengths |
| Thin | Thin out dense controller, pitch bend and aftertouch data, as Sequencer Plus Gold's did |
| Filter | Delete events matching a condition, e.g. velocity below 20 |
| Split | Move notes above or below a pitch to another track |
| Remap | Change a CC number or a note (events carry no channel: the track's applies) |

**How transforms are reached and set (decided November 2026, for milestone 6's step 10).**

- **Both orders.** `!` takes a range and then opens the transform menu (`!ib`, then a letter); each `, x` entry is the other way round, the transform first and then a range, as `^gn` is. On a Visual selection either acts at once. As built: the menu is the `, x` group itself, `!`'s range kept while its keys wait, so the hint menu shows it at once and the transforms a user binds elsewhere move it with them (the keys their bindings share); Escape or a key it hasn't gives it up. `^`, `q` and `~` are in it too. At the `:` prompt a transform takes the selection, or else the cursor's bar, as a doubled operator does, and asks as its keys do when given nothing (`:transpose`).
- **Asking, as `^` does.** A transform needing an amount asks at the prompt, its label saying what and with its defaults filled in ("Compress velocities of 12 notes (50%, window=1bar): "), so Enter takes them; one with an obvious default (retrograde, clean up) just runs. Each has a `:` command taking its amount and `name=value` options, given there it asks nothing, and `.` repeats it as it was answered. The hint menu shows each default in its description.
- **Asked in turn (decided November 2026; built for compress, expand, phrase and quantise).** A transform with several settings asks for each in turn, its default shown and taken by Enter, Tab listing its choices where it has some, rather than taking them as `name=value` options in one answer: the transforms are seldom used, so their settings aren't remembered and a few Enters don't matter, while the quick operators (`q`, `^`) stay immediate. Compress, expand and phrase (now taking `window=`, `centre=` and `threshold=` in one answer) change to match; `.` repeats every answer. A setting given in the `:` command is not asked for.
- **10e's transforms (decided November 2026):** the menu's quantise (`, x q`, `:quantize`, built) asks for the grid (the track's, at Enter, so Enter throughout does what `q` does; `grid` for each track's own where they differ), the strength (100%), the swing (50%, straight; 25% to 75%, below 50% putting the off-beats early, a pushed feel) and what to move (`starts`, as `q`, `ends` keeping starts, `both`, or `lengths` rounded to whole grid steps); a note too short to keep an end of its own, its start and end going to one line, is a step long instead, from its start with `both` and to the next line with `ends` (decided November 2026, after use: it had been left alone), and about the pedalling as `q` does. Time stretch, `, x s` (built, `:stretch`), asks for a ratio (`2` half time, `1/2` double time, `150%`) about the range's first event, every event in the arrangement and the event list and the notes in the piano roll, as shifting takes them, not rippling: what it runs into it overlaps, a note onto another of its pitch refused. Note lengths, `, x n` (built, `:length`, and `:legato` asking nothing), asks for `legato`, a length (`1/8`) or a percentage (`80%`); legato holds each note or chord until the next one's start, but for the last in the range, which keeps its length, as there's nothing in the range to say how long (decided November 2026: include the note to join up to in the range).
- **Keys moved (decided November 2026):** `, x s` is Stretch, and shaping velocities moves to `, x p`, Phrase dynamics (`:vel-phrase`, 130% bigger swells, 70% flatter), as "shape" said little.
- **The quick operators stay quick.** `q` quantises to the track's grid at once, as `qq` and `qib` do now; the transform menu's quantise (`!ib q`, `, x q`, `:quantize`) asks, the grid filled in, so Enter does what `q` does, Tab listing the note lengths, with strength, swing and starts or ends alone as options (decided November 2026: the transforms are the slower, more flexible way, where asking is reasonable).
- **Defaults to begin with, to be tried and tuned:** the soft knee eases relative velocity changes within 16 of each limit; compress, expand and shape average over a bar, centred on each note; the interactive step sizes (for adjusting by ear) are 10% for amounts in percent, 5 for offsets and 5 ms for the pedal offset.

**One definition each (November 2026, after a code review).** Each transform is one entry in a table (`src/ui/transform_specs.cpp`): its command's name, aliases, usage and description, how it asks (for nothing, one thing, its settings in turn, or a key and the rest), its question, examples and default, its settings, and the function that does it. Its command is made from the table, in every view; a test checks that each takes the defaults it offers, and another that no two commands share a name or an alias. Adding one is an entry, its function, and its key in the modalrc.

**Keys and scales (decided November 2026).** Few songs keep one key throughout, so a transform needing a key (transpose in key, inverting in the scale) asks for it each time, rather than the song having a single key and scale: "Key for 12 notes in Piano (D dorian): ", the last used filled in, so Enter takes it again. Up and Down go through the keys used lately (a history of their own, as `/`'s), Tab completes and lists the keys and scales there are, and naming the key in the command (`:transpose-key +2 key=Eb lydian`) asks nothing; `.` repeats with the same key. Marked key changes and a song-wide default key come later, and a MIDI file's key signatures with them.

- **The scales built in:** major (ionian) and minor (natural, aeolian), harmonic and melodic minor, dorian, phrygian, lydian, mixolydian and locrian, major and minor pentatonic, blues, whole tone, and the two diminished scales. Others are defined in the modalrc by their degrees, as `scale hijaz 1 b2 3 4 5 b6 b7`.
- **Scales of any size:** a degree is a step of the scale, five to the octave in a pentatonic one.
- **As built (November 2026):** `, x T` transposes in a key (a capital, as the variant of `, x t`, decided November 2026 on trying `, x k`), `, x i` inverts chromatically and `, x I` in a key, about the range's first note at Enter (the lowest of a chord), and `, x R` retrogrades, mirroring the rhythm over the notes' own span, from the first's start to the last's end. A key in a question is a tonic, spelled as typed, and a scale's name or alias (`D dorian`, `F# aeolian`), a tonic alone for major and `Dm` for minor; its question comes first, the amount or pivot after it. The scales are named in one word each (`harmonic-minor`, `major-pentatonic`, `whole-tone`, `diminished` for whole-half and `dominant-diminished` for half-whole). The keys typed are kept for Up and Down for the session, not between sessions (decided November 2026). The key offered at Enter is the one the range's notes fit best, by Krumhansl and Schmuckler's key-finding (the time each pitch class sounds against the major and minor keys' profiles), or the last used where there are fewer than six notes to tell by; Tab on the empty line lists the best three and the other scales on the best one's tonic that hold as much of the notes, as dorian may, since the profiles can't tell a mode from its major (decided November 2026).
- **The search prompt helps too (decided November 2026):** until something's typed, it shows dimmed what a search can look for (`C4 F# >A3 A3-A5 vel<60 len<1/16 cc1=127 bend inside KEY outside KEY`), and Tab completes the keywords, and tonics and scales after `inside` and `outside`.
- **Searching by key (decided November 2026):** `/outside D dorian` matches the notes not in the key, and `/inside D dorian` those in it, so `n`, `, S T` and `^gn` find and fix wrong notes as other searches do.
- **Notes outside the scale** keep their distance above the scale's note below them, so a chromatic passing note stays one, transposing in key and inverting in the scale alike.

**Thin and filter (decided November 2026).** Two transforms, not one:

- **Thin** thins out dense continuous data, as Sequencer Plus Gold's did: hundreds of mod wheel (CC 1) events from one gesture, or pitch bend or aftertouch, down to what's needed. Its first setting says which (`cc1`, `bend`, `aftertouch`; `all` by default, every kind of continuous data in the range, but never the switch controllers such as the pedals), `per=` the most kept in a quarter note (16), and `step=` the smallest change in value worth keeping (2). The first and last events of each gesture are always kept, so it ends where it did.
- **Filter** deletes the events matching a query, written as `/`'s are (`:filter vel<20`, `:filter cc7`); from `!` it takes the search's query, if there is one, filled in.
- **Which controllers thin (decided November 2026, after a code review):** an explicit list of those that are curves (modulation, breath, foot, portamento time, volume, balance, pan, expression, the effect and general purpose controllers, the sound controllers 70 to 79, the effects depths, and the undefined controllers knobs are often set to), never bank select, data entry and increment, the RPNs and NRPNs, Hold 2, portamento control, channel mode messages or the least significant halves, each an action or part of one, nor (decided November 2026, after a second review) the high resolution velocity prefix, CC 88, which belongs to the note after it.
- **Thin is for continuous data alone (decided November 2026):** controllers that aren't switches, pitch bend and aftertouch, never the switch controllers (sustain, sostenuto, soft, legato, portamento), even with `all`, where thinning by density could drop a change that matters; `:thin cc64` is refused, pointing to the pedals' clean-up. Repeated pedal events are the pedalling tools' Clean up's (10g): exact repeats only (so half-pedalling's values are kept), flicker merged, and the first and last events in the range always kept.
- **10f as decided (November 2026),** each asking its settings in turn: Thin, `, x d` (density, as `, x h` is humanising's; built), which data (`all`, `cc1`, `bend`, `aftertouch`), the most a quarter note (16) and the smallest change (2), each gesture's first and last kept; Filter, `, x f`, the query, the search's at Enter; Split, `, x y`, the pitch (C4), which side moves (`above`, the note itself with those above it, as a split point's note goes with the right hand, or `below`; decided November 2026, after `up` and `down` read awkwardly) and the track to move them to, Tab listing the tracks and a new name making a new track (so a piano part splits into hands); as built, the track offered at Enter is a new one named after the first's and the side (`Piano high`, `Piano low`), put after it and playing to its port and channel; Remap, `, x m`, what (`cc1`, or a note, `C1`) and what to (`cc11`, `D1`), limiting velocities moving to `, x M`. Channels aren't remapped, as events carry none.

**Velocity without clipping (decided October 2026)**

Adding a fixed amount clips loud notes at 127 and soft ones at the floor, flattening the dynamics, so velocity changes avoid hard limits by default:

- **Lift and lower by headroom.** `:vel-lift 25%` moves each note a quarter of the way towards 127, and `:vel-lower 25%` a quarter of the way towards the floor, keeping the notes' order and proportional spacing; nothing reaches the limit.
- **A soft knee on relative changes.** `+10` (in the inspector, the command line or the `^` operator) and percentages (`120%`) change the amount in the middle of the range but ease off smoothly near the limit being approached, not the one being moved away from. `:set velclip=hard` gives plain clipping. The step keys (`Ctrl-a` and `Ctrl-x` in the piano roll, the field steps in the event list) stay exact, one a press, clipping at the limits (decided November 2026): eased, a press near the top could round to no change, and 127 couldn't be reached.
- **Single names (decided November 2026):** `:vel-lift`, `:vel-lower`, `:vel-limit 20-110` and `:vel-ramp`, and so on, rather than `:vel` and a word, so they complete and show in the palette as every other command does.
- **The ramp:** `:vel-ramp 60-100` sets velocities from 60 at the first note to 100 at the last, by time, a chord's notes alike; `:vel-ramp 80%-120%` scales the notes' own velocities by a changing amount instead, keeping the playing's shape (decided November 2026).
- **A floor,** 1 by default and configurable. Velocity is never set to 0, which means note-off.

**Velocity compress and expand over time**

Two timescales for two aims, evenness from note to note and the shape of a phrase, working relative to a moving average:

| Command | Effect |
| --- | --- |
| `:vel-compress 50%` | Pull each note halfway towards the local average: evens out note-to-note unevenness, keeps crescendos |
| `:vel-expand 50%` | Push notes half as far again from the local average: sharpens accents |
| `:vel-phrase 130%` | Exaggerate the phrase's contour (the moving average itself): bigger swells, the same note-to-note detail |
| `:vel-phrase 70%` | Flatten the contour: a more level part |

As built (November 2026): the window is centred on each note, `window=` taking bars at the note's meter (`1bar`, `2bars`) or a note length (`1/2`); `centre=` takes `local`, `average` or a velocity; `threshold=` takes `>90` or `<30`; the answer to the question can be the options alone, the amount taking its default. Each setting is asked for in turn (changed November 2026 from options in one answer, after use; see Asked in turn): its question with its default, how it's written dimmed after the answer until something's typed (`1bar|2bars|1/2`, `local|average|N`, `all|>N|<N`), and Tab listing its fixed values; an answer can give later settings as `name=value`, which aren't then asked for, commas between them taken. At the `:` prompt Tab completes the settings' names and values (`centre=average`). A chord, for the chord tools, is notes starting within `chordwindow` of its first, as `gk` and `gj` take them. Compress and expand say the direction, and the percentage how much (decided November 2026, as an audio compressor's amount): compress takes away that much of each note's distance from the average, up to 100% (every note on it), and expand adds that much again; shape, with no opposite, is a factor of the contour, 100% leaving it as it is. Options: `window=` the averaging window (`1/2`, `1bar` by default, `2bars`; a larger window treats more as phrase shape); `centre=` the local average (default), the selection's average or a fixed value; `threshold=` to act only on notes above (or below) a value, like an audio compressor taming peaks. All use the soft limits above, and compress and expand also work within chords.

**Chords and voicing balance**

Notes in a chord share a start, so their velocity bars would overlap. In the velocity lane a chord's bars fan out side by side within its column, low to high, and `Tab` steps through the chord's notes there. In the note area, `gk` / `gj` move through the chord's notes and the field step keys change the current note's velocity, with counts. On any chord note the inspector shows the chord's range (`vel 64–90`); `^ic 80` sets every note, and a relative change (`^ic +10`) moves them all, keeping their balance.

| Transform | Effect |
| --- | --- |
| Accent top note | Top note up by N and the others down by N, to bring out a melody |
| Balance by pitch | A straight velocity slope from bottom to top (e.g. 70 → 95), or reversed to bring out the bass |
| Compress / expand within a chord | Pull the chord's velocities together or push them apart about their average, keeping the overall level |

These apply to one chord, or to every chord in a range (accent top note over `ib` voices a whole bar of chords).

**Pedalling (decided October 2026)**

Switch controllers (sustain CC 64, sostenuto CC 66, soft CC 67, legato and portamento; the set is configurable) are edited as regions rather than value curves (see Views: piano roll). Their tools:

| Tool | Effect |
| --- | --- |
| Re-pedal at chord changes | Pedal down just after each chord change and up just before the next, with a configurable gap (legato pedalling), replacing the range's sustain |
| Re-time | Keep the performed pedalling, moving each lift and press near a chord change to just before and after it, the rest left as played (added November 2026, as not every chord wants pedalling) |
| Pedal per bar / beat | A fresh pedal on each bar or beat across a range |
| Clean up | Merge overlapping or flickering pedal events |
| Clear | Remove the pedalling from a range |
| Offset | Move every pedal change in a range slightly later |
| Bake | Turn pedalling into longer notes, for instruments that ignore sustain |

As decided and built (November 2026), in the transform menu's `, x P` group, each asking its settings in turn: re-pedal `r` (lift before, 10 ms, and press after, 60 ms, from `pedallift` and `pedaldown`), re-time `t` (the same, and how near a change counts, 200 ms), each bar or beat `b`, clean up `c` (exact repeats, so half-pedalling's values are kept, and flicker within 30 ms, the first and last events in the range kept), clear `x` (sustain, sostenuto, soft or all), offset `o` (20 ms, `-20ms` earlier) and bake `k`. They act on the range's time on each of its tracks, in the piano roll too, where a range takes only notes. A pedal down as the range starts is lifted there and one down as it ends pressed again there, so what's around the range is as it was; nothing they write goes at or past the range's end (decided November 2026, after a second review), so a re-pedalled lift that would fall there is left out where the pedal is held on past it, and comes at the end at the latest where it isn't. Re-pedal, re-time, each bar or beat and bake are for sustain alone; clean up and offset take all three pedals.

**Adjusting by ear (agreed design, November 2026).** This is part of looping's design.

Any velocity transform, and the pedal offset, can run interactively: run the command on a selection and the selection loops; `k` / `j` change the amount (compression 50% → 60%), applied live as it plays, with the amount and step shown in the status line; `Enter` accepts and `Esc` cancels, restoring the original. The whole adjustment is one undo step.

## Views

The arrangement is the home view; Enter on a track opens it in the piano roll for detailed editing, and the event list shows the exact data. All three share one cursor position and selection, so switching views (or `, v`) never loses your place. A status line and transport bar are always visible.

- **One cursor, shown by each view (decided for milestone 5).** The cursor is one position in the song, shared by the views: a track, a time (a tick) and a pitch, and the note it's on, if any. The arrangement shows it as the bar of that track holding the time; the piano roll as a crosshair at the time and pitch; the event list as the row at the time, or the note's own row when the cursor is on a note, so going from the event list to the piano roll and back lands on the same row. Opening the piano roll from the arrangement keeps the time (not snapping to the bar's start) and takes the pitch last used on that track, or the middle of its notes the first time; going back, the cursor is on the bar holding it. Each view keeps its own scroll and zoom, so a view comes back as it was left, as Vim's buffers do.
- **Moving between views (decided for milestone 5).** Enter on a bar in the arrangement opens that bar in the piano roll: the page holding it, at the page size last used on that track, the cursor at the bar's start; Enter keeps to editing, as in the event list. With a selection of bars (milestone 6), Enter opens exactly those bars as the page, and turning the page then moves on by as many bars, until the zoom changes and pages fall back into line with the section. As built (October 2026): on the cursor's track, from `v`, `Ctrl-v` or `V` once an object has set its time, as many bars as there, up to the most a page holds (16, its first bars beyond that); whole tracks open as Enter does; another track, or zooming, ends it. Backspace goes back to the view the cursor came from, like a browser's back button (rather than Escape, which Vim users press often just to be sure of Normal mode, and which cancels a count or operator). Until the leader menu, `ga`, `gr` and `ge` go to the arrangement, the piano roll and the event list; single keys may be better in the end, to settle in milestone 6's review of the key map.
- **The selection is an area (decided for milestone 5).** What's selected is an area: a time range on a set of tracks, optionally narrowed to a range of pitches ("bars 5–8 of Bass and Drums"; "bars 5–8, C3 to G3"). Whatever is inside it is selected, the same in every view, and it survives switching views. Operators act on the events within it. Picking notes that an area can't hold, scattered ones and not their neighbours, comes later: from searches (milestone 6), and by adding or removing the current note from the selection by hand, where a search can't easily say what's wanted; so the model leaves room for a selection that is an area plus notes added or taken out.
- **Moving a selection (decided 10 November 2026).** The first successful piano-roll move retains the notes taken before the move. Later moves, highlighting and content edits use that same set at its new positions, so crossing another note does not select or move it. If snapping off-grid notes changes their spacing, the selection bounds expand to include all retained starts. Escape and `gv` retain the set; deliberately extending the selection with cursor motions, choosing another object or changing Visual kind establishes an area selection again. Existing collision and before-zero refusals remain atomic. Repeated moves of the same kind undo together only within one unchanged Visual interaction; leaving Visual mode or deliberately redefining its selection ends that merge. Recalling it with gv starts a new interaction. Explicit outer undo groups, such as macros, remain atomic. Operations expressly on a range's time keep their documented time semantics.

- **The workspace and the views, as built in milestone 5.** A workspace holds what every view shares: keys, counts and pending operators, the `:` prompt and messages, the status line, playing and following the playhead, undo, `:port` and the unnamed register. Each view (the event list, the arrangement and the piano roll) does the rest its own way, through one interface: its commands, an operator over a motion, drawing its area, its bar and the inspector, the shared cursor, where an edit was made for undo, and showing the playhead. Commands are registered once, by name; one a view shares with another (`cursor-down`) goes to the view shown, and one it doesn't have says so ("Zoom in isn't in the event list"). Modal opens in the arrangement, the home view. The shared cursor's pitch is none until a view has one to keep (a note's in the event list, the piano roll's, or the one last used on a track in the arrangement), so the piano roll can tell a first visit, where it starts at the middle of the track's notes.
- **The arrangement, as built in milestone 5 (step 1).** Milestone 3's sketch, now a view of the song as it is: the track's bar and the inspector above it (the cursor's bar: its position, time, number of the song's bars, meter, the notes starting in it and its section), the ruler with the play-from marker (▶ in the labels' row, whose names stop short of it or start after it, moved there in October 2026 from among the bar numbers, where it covered them) and the playhead (a line through the ruler and tracks, kept a third of the way across while playing, the view gliding smoothly under it rather than stepping a column at a time, which made the playhead jump back at each step), and the tracks. `h` / `l` (and `{` / `}`, `[b` / `]b`) move by the track's bars, `j` / `k` (and Ctrl-PageDown / Ctrl-PageUp) between tracks keeping the time, `0` / `$` and `gg` / `G` to the first and last bar (`5gg` to bar 5), Ctrl with the motions and `Ctrl-D` / `Ctrl-U` / `Ctrl-F` / `Ctrl-B` scroll, `zz` centres, `]s` / `[s` and `]l` / `[l` go to sections and labels, and `zi` / `zo` / `z0` zoom (decided for milestone 5, as Vim's `z` family; `z0` because `zz` centres).
- **Operators in the arrangement (decided for milestone 5).** `d`, `y` and `p` work on areas of bars: what an area owns is the events starting in it, notes whole even where they sustain past its end (see Notes crossing a range's edges in decisions.md). `dd` is the cursor's bar, `3dd` it and the next two, and `dG` from it to the end, rather than the whole track, which a line in Vim would suggest but which is too big to hit by accident. Motions across bars take bars of the cursor's track, ending before the bar they land on as Vim's character motions do (`d2l` is this bar and the next; `dh` the bar before), except `G` and `gg`, which take the bar they land on too, as Vim's line motions do. Motions across tracks take the cursor's bar on each track they cover (`dj` is this bar here and on the track below, `y2j` on three tracks), so the unnamed register holds an area: a list of events for each track, from the top track down, their ticks from the area's start. `p` puts it at the start of the cursor's bar, onto the cursor's track and those below, merging with what's there; the event list puts it at its cursor's time the same way. A Visual selection (milestone 6) is the more deliberate way to the same areas.
- **The piano roll, as built in milestone 5 (step 4a, viewing and moving).** `gr`, or Enter on a bar in the arrangement (at the bar's start), opens the cursor's track in the piano roll. The page header is the view's own bar, rather than a row of its own: the track, its channel and port on the left, and on the right the section, the bars in view in the track's bars, and the cursor's place (the grid moved to the status line and the new note to the inspector in November 2026, after use). The inspector shows the current note as the event list's does, or on an empty spot `No note` with the cursor's position, time and pitch. Above the notes, a ruler of two rows (decided October 2026, after use, since a view can run on into the next section): the sections as blocks in the arrangement strip's two shades, each named in the colour of its line from where it shows, the names drawn straight on the blocks (as on the arrangement's strip too, whose names take the line colour as well) rather than on a background of their own, which stood taller than the block, so a section begun before the view keeps its name at the left edge; the labels by name and the play-from marker ▶, names stopping short of the next or of ▶, or starting after ▶ when they're at the same place; and below, the bar numbers in the track's bars, every so many bars from each section's first if they're crowded. Each section's start is a line down through the notes and the lane, stronger than a bar line, and each label a faint one. Below them, the keyboard column (note names, C's bold, black keys' rows shaded across the page, the cursor's pitch highlighted), the notes, and a velocity lane three rows high with its bar lines. Notes are drawn at their exact places: a solid start half a cell wide, then a lighter body, both brighter the louder the note, a pixel short of the next; the current note in the accent colour. The cursor is a faint band along its row and down the time it covers, through the lane, with that span boxed: the current note's start to end, or on an empty spot the length of the default note from the cursor, the note `o` would add, so it shows what you'd get (decided October 2026, rather than the grid step, which looked odd on short notes under a wide grid). The playhead is a line through the notes and lane, and the pages turn with it; while the cursor doesn't follow it (with rewind on), the view comes back to the cursor when playback stops, as the event list's does (decided October 2026, after use: the pages had stayed put while the playhead went off them). Motions: `h` / `l` by grid steps counted from each bar line (from off the grid, to the steps either side first), `{` / `}` (keeping the place in the bar), `[b` / `]b`, `0` / `$` (the bar's start and last grid step), `gg` / `G` (the song's start and its last grid step, or bar {count}), `]s` / `[s`, `]l` / `[l`, `Tab` / `Shift-Tab` to each note's start in time and then low to high, landing on its pitch, and `(` / `)` to each chord's start, on its lowest note; `k` / `j` a semitone, `K` / `J` an octave; `Ctrl-j` / `Ctrl-k` and `Ctrl-D` / `Ctrl-U` / `Ctrl-F` / `Ctrl-B` scroll the pitches with the cursor, and `zz` centres on its pitch (then later in time too, and `Ctrl-h` / `Ctrl-l` and `Ctrl-{` / `Ctrl-}` scrolling in time: see Piano roll pages); `zi` / `zo` / `z0` step the bars to a page; Ctrl-PageDown / Ctrl-PageUp go between tracks (not the conductor, which has no notes), each track keeping its pitch and page size. Motions past the song's end fail, as in Vim. Decided while building it: `J` stays bound to `join`, which the piano roll takes as an octave down, since one key can't be bound to two commands; and operators came with step 4c (see Editing notes, under Moving and editing notes).
- **The grid and default note, as built in milestone 5 (step 4b).** Each track's grid and default note are track settings, saved in the song. `zh` / `zl` (and `z` with Left / Right) halve and double the grid from 1/64 to a whole note, keeping triplets (first built the other way round, which felt reversed in use); `Ctrl-t` turns triplets on and off; `:grid 1/8t` sets it, and `:grid` alone shows it. `, n` takes the current note's length and velocity as the default note (on an empty spot it says there's no note); `:len 1/4` sets the length, `:len grid` links it to the grid again, and `:len` shows the default note. The status line shows the grid with the settings (`Grid 1/16`), and the inspector's right the note `o` would add, stacked: `New note`, `Length: grid`, `Velocity: 100`, dim as `e` doesn't edit them, left out where a note's fields need the room (decided November 2026, after use, as the note is the cursor's, and the grid the view's). Changes are undo steps (decided October 2026), with grid steps one after another on a track merged into one (so `u` after several `zh` goes back to the grid before them), unless the song was saved between; steps that bring the grid back to where it was leave no step.

- **Arrangement (home view).** One row per track, cells shaded by note density, with labels along the top. Since tracks can have different meters (decided in milestone 3), a column is a fixed length of time at the current zoom (such as one beat of the reference meter), not a bar: the track headers are text cells, but each row's timeline is a pixel region where the track draws its own bar lines at their exact positions, and the cursor is an exact span of time (such as bar 5 of that track) drawn to the pixel. The ruler numbers the conductor's bars. Used for navigating the song and for whole-section operations: copy verse to bar 33, mute tracks, set loop range. The ruler marks each tempo change with `▲` and whole BPM in the `event-sign` colour, leaving out the song's first tempo and sections starting at the tempo already in force (November 2026). The piano roll's ruler marks them the same way (November 2026). The section strip (below) sits in the ruler, above the bar numbers, whose row is shared by the track column's heading, directly above the names and ready for any column headings beside them (November 2026). The inspector on a bar shows its position, number, meter, and counts of notes and other events, which together shade it; on a section, the name under the Section heading, then its position, bars, meter and length, so Bars and Meter sit where a bar's do.
  - **As sketched in milestone 3's test view** (confirmed in milestone 5, with the changes in The arrangement, as built). Each bar is a block as wide as the bar is long, as SPG's squares but in proportion, so a 7/8 bar is 7/8 as wide as a 4/4 bar. Blocks are shaded in four levels by how many notes start in the bar (theme roles `density-1` to `density-4`); a bar with no notes is a faint line, and an empty track shows a dot on each bar line. A small gap separates blocks while a column holds no more than a whole note; zoomed out further, the gaps go, since the song's overall shape matters more than single bars there. Labels are faint lines at the same time on every track whatever their meters, beneath the blocks and text, through the ruler (broken only where a label sits across them) and across the tracks; and are named in the ruler, each name cut short with an ellipsis at the next label, or left out if fewer than three characters fit. The ruler also shows the reference meter's changes (the conductor's), each named if the name fits before the next change and otherwise shown by a tick, so a single bar in another meter never hides the change after it; and its bar numbers, counted in sections that start at bar 1 and at each label's bar, so the numbers follow the song's structure: each section's first bar, then every n bars into it, where n (1, 2, 4, 8...) is the fewest bars that leave room for the widest number in the shortest bar. A number shows only if it fits before the next section's, so the sections' numbers come first. Track headers show no meter, since a track's meter can change along it; the bar above shows the meter at the cursor. The cursor is one bar of its track, boxed on all four sides; `h`/`l` move by that track's bars and `j`/`k` keep the cursor's time, landing on the bar that contains it, so going back up returns to the same bar. SPG's highlighting of every eighth bar isn't used, since sections often run to 6 or 12 bars, or have an extra bar; it could be an option later. The sketch predates sections: in the real view, the ruler's numbering restarts its counting at each section rather than each label, and section boundaries are the faint lines down through the tracks, with labels drawn more lightly.
- **Piano roll (track editing).** Pitch rows against time, drawn on the grid with pixel-precise note starts and lengths inside the cells. A velocity lane underneath shows bars per note. The cursor is a crosshair, a position in time plus a pitch, and doesn't have to sit on a note. When it is at the start of a note or inside one, that note is the **current note**: the inspector shows it and operators act on it. On an empty spot, the inspector shows the position and pitch only. Motions are in Editing grammar.
- **Event list (exact data).** One row per event: bar:beat:tick, type, channel, data fields (pitch name, velocity, duration). Every field is a cell you can move to and edit directly, with `Ctrl-A` / `Ctrl-X` incrementing and decrementing as in Vim. Filters show only notes, only CCs, a pitch range, etc.
  - **Decided for milestone 4.** The list shows one track at a time, as in SPG, with Ctrl-PageDown / Ctrl-PageUp to change track (replacing the original `gt` / `gT` in November 2026). Tempo changes, meter changes, section starts and labels are listed dimmed in every track's list, at their positions. The conductor track (decided October 2026) has a list of its own too, reached with Ctrl-PageDown / Ctrl-PageUp like any track, or directly with `gc`, where its tempo and meter changes are edited. `j` / `k` move between events and `h` / `l` between an event's fields, like a spreadsheet; the time motions (`{` / `}`, `[b` / `]b`) move the cursor by time, to the event at or after where they land, and never move notes, which the Alt keys do. Enter edits the field under the cursor in place, as a small prompt in the cell, where any character is typed (so `-40` and `+10` can be entered); in Normal mode, `+` and `-` step the field under the cursor, with counts, and `Ctrl-A` / `Ctrl-X` do the same for Vim habits. The inspector shows the event under the cursor; editing its fields with `e` comes with the piano roll (milestone 5), where a note's fields can't otherwise be reached.
  - **Motions in the event list (decided in milestone 4).** They're for getting about, not marking out time, since the event list is for exact tweaking of events rather than editing in time, and its cursor is always on a row; there are no placeholder rows for empty time, which some tracks would have thousands of. `}` / `{` (the same place a bar on or back, keeping to that place while repeated, through shorter bars) and `]b` / `[b` (a bar line) work in the track's own bars from the cursor's row, with counts, and go to the first row at or after where they land. Going back, if that row isn't earlier in time than the cursor's, the motion is taken again from there until it is, or reaches the start, so it never sticks: `{` means back a bar at a time until there's an event. `)` / `(` go to the next or previous chord: events starting within `chordwindow` of the first of them (30 ms by default, in milliseconds since it's about how a person plays, not a musical length, so it's the same at any tempo; measured from the first event, not chained, so a fast run isn't one long chord); from inside a chord, `(` goes to its start first. `]s` / `[s` and `]l` / `[l` go to a section's start or a label, on its own row; going back from a section's start (or an event at it) goes to the section before. `0` / `$` stay the first and last field in the event list, since `[b` goes to the bar's start; the piano roll keeps the design's meaning, the start and last grid step of the bar.
  - **Operators in the event list (decided in milestone 4).** `d` and `y` take a motion, with counts that multiply (`2d3j` is `d6j`), and work on rows as Vim's operators do on lines: `j`, `k`, `gg` and `G` take whole rows, the one landed on too (`dj` is this event and the next); the time motions stop before the row they land on (`d]b` deletes from this event up to the first at the next bar line; `d[b` from the first at the bar line before up to this one). Pressing the operator's key again is the event under the cursor (`dd`, `3dd`), and `x` is the same as `dd`, since a list has no characters to delete. (Revised October 2026: `dd` is the cursor's bar's events, and `x` and `Y` the event; see Ranges, objects and putting in decisions.md.) Only the track's own events are touched: the conductor's rows and the end row are passed over. In operator-pending mode the Normal mode's motions work through their own bindings, unless `omap` binds those keys, and any other key gives the operator up, as in Vim. Commands say they're motions in the command registry. One unnamed register holds the events yanked or deleted, their times from the first's, so putting keeps their timing in any meter; yanking says how many. `p` puts them with the first at the cursor's time, merged in without overlapping notes of one pitch, by the recorder's rule (whichever starts first ends where the other starts, and at the same tick the new one wins). Each change is an undo step titled for an undo list ("Delete 3 events in Bass"); `u` and `Ctrl-R` (and `:undo`, `:redo`, with counts) go back to where it was made, on the same row among those at its time, saying "Undid: …". The conductor's list is edited with field editing (see Field editing in the event list), which also brought `o`, adding a note and going straight into editing its pitch. The view's messages in the status line start with a capital, as Vim's do ("Nothing to undo", "2 events yanked"); config errors keep their `modalrc:3: …` form.
  - **Field editing in the event list (decided in milestone 4).** Enter edits the field under the cursor in its cell, holding its value as shown, without a note value or note number in brackets; typing replaces it, as in a spreadsheet, and the editing keys (the arrows, Home, End, Backspace) keep it; Enter sets it and Escape leaves it. A value out of range, or an edit that would make a note overlap another of its pitch, keeps the prompt open with a message saying why (naming the other note: "Would overlap the F1 at 2:1:000"), to put right; an overlap is refused rather than resolved, since resolving would silently shorten or replace a note out of sight (putting, a deliberate paste, keeps the recorder's rule). A field takes a value or a change with `+` or `-`: a position as bar:beat:tick (or bar:beat, or bar) or a change of bars:beats:ticks or a note value (`+1/16`, `-0:0:010`); a pitch by name or number, or semitones; a velocity 1–127 (never 0, which is a note-off), a value 0–127, a bend −8192 to 8191; a length as bars:beats:ticks in the meter where the note starts or a note value; text as typed; SysEx as hex bytes. `+` and `-`, and `Ctrl-A` and `Ctrl-X`, step a field with counts, kept within its range: a value, release or bend by 1 (bend's step to be judged in use), a pitch by a semitone, a position by a beat of the meter where the event is, a length by a 1/16 note until the per-track grid (milestone 5). An edited event takes the cursor with it when it moves. Each edit is an undo step ("Set velocity in Bass"). `o` shows a new note row after the cursor's, at its time, with the velocity and length of the note before (or 100 and 1/8), and edits its pitch; Enter adds it as one step, Escape leaves nothing. In the conductor's list, Enter and the steps change a section's or label's name, a tempo (stepped in whole BPM) or a meter (its top stepped); a meter that a change soon after, such as a remainder bar, leaves no room for is refused with a message naming that change; `dd`, `x` and `d` with a motion delete tempo and meter changes and labels, but not a section's own tempo and meter at its start, nor a section, which are joined later. Moving the conductor's changes, and adding them, come later; yanking and putting are for track events only. Several events at once wait for Visual mode (milestone 6).
  - **As built in milestone 4.** The columns are the position, the event's type, then its fields: Data (a note's pitch as name and number, `E1 (28)`, a controller, a program, or a name, text or SysEx bytes, which run on to the edge), Value (a velocity or value), Length and Release, under headings that stay put as the list scrolls; each field is a cell the cursor can be on, and `h` / `l` keep to a field as the rows change, as Vim keeps to a column. Positions are in the track's own bars, the ticks padded to a quarter note's width (three digits at 960 PPQN), so the columns line up. A note's length shows as bars, beats and ticks in the meter where it starts, with in brackets the common note value it is or is within 5% of, if there's one: `0:0:480 (1/8)`, `0:0:492 (≈1/8)`, or `0:1:252` alone (decided in milestone 4). The common values are those with denominators up to 16: straight from a whole note to 1/16, dotted and triplet to 1/8. and 1/8t, and whole notes beyond. Showing only the nearest value with ticks over or under (`1/8 + 12`) was tried first, but recorded files gave values like 13/48 and a straight note named as a triplet less 95 ticks, which no musician would use. Editing takes bars:beats:ticks or a note value, and relative changes of either, `+1/16` or `-0:0:010` (see Field editing in the event list). The 5% is to be checked against real files. At one tick the rows are a section start, then meter, tempo and labels, then events in the order they're sent. The conductor's rows in a track's list are only there to find the way by, and are changed only in the conductor's own list (decided in milestone 4), so that changing them never changes other tracks unseen and editing notes never deletes a tempo; the cursor still lands on them. A track's own meter shows undimmed. The last row is the end of the song, where the cursor can sit in an empty track. The conductor's list is track 0, before track 1, so Ctrl-PageUp from track 1 goes to it and Ctrl-PageDown from the last wraps round to it. Counts move that many tracks; `3gt` now opens track 3 in the Tracks view. The list opens on track 1. The top bar names the track, its channel and port, and the section the cursor is in with its bars; the bar's right gives the cursor's position, time and meter, and the status line the transport (see Status line and transport). `modal FILE` opens a `.modal` song or imports a `.mid` file (not to be saved over); without one it starts a new song, and `modal --demo` opens the demo song from the arrangement sketch (see A new song).
- **Status line and transport.** Contents set in configuration (see Customisation). While a field is being edited, it says what the field takes and what the keys do there, Up and Down stepping it included (November 2026). **Where things go (decided November 2026, after use).** Each of the three places has its own subject, rather than repeating another: the **bar at the top** is where the cursor is, the **inspector** what's under it, and the **status line** the transport, with the modes and settings, the file, and messages and hints. The top bar names the cursor's track, its channel and port, and the track's quantise, program and bank where set; in a view with a timeline, it then gives at the right the cursor's section and the section's bars, and its position, time and meter, labelled (`Position:`, `Time:`, `Meter:`). The Tracks view has no timeline, so its bar names the track alone. The status line starts with the mode, then the transport, always shown: stopped, a dim ■ and the play-from marker's position, time, meter, tempo and section, where Space will start; playing, ▶ and the playhead's, counting on from there, in the accent colour. Messages, hints, selections and an operator's description follow it, so they never cover it. The right side holds the settings (Quantise bypassed, the piano roll's grid, padded so Rewind stays put, and Rewind) and the song's file. The tempo is the transport's: at the marker when stopped, at the playhead while playing. So nothing moves as values change, each part is as wide as the song needs: the mode as the widest mode, the position and time as the song's end needs (right-aligned, as a counter), the meter five characters, the tempo as the song's widest, the section as its longest name up to 16 characters, and room is kept for the file's `[+]`; in the top bar the track's name and port are padded to the song's longest (up to 32 and 24 characters), and what varies most goes at an end. Where the top bar is too narrow for everything, it leaves out first the track's quantise, then its program, then its bank, then the section's bars, then the section, and never the track or where the cursor is.

**The Tracks view (first implementation built November 2026, milestone 7)**

A table of the song's tracks and their settings, inspired by Sequencer Plus Gold. The Tracks view shows the parts, their routing and how they play; the arrangement shows where each part plays, and the outline shows the sections' running order. It is a view of the same tracks, with the shared cursor's track and remembered musical position, rather than another copy of their settings.

- **Columns.** Track number, name, Mute/Solo/Arm/Thru/Chase and Q buttons, input and output ports, channel, bank MSB, bank LSB, program, transpose, velocity offset, time offset, then quantise settings, last as they can run long. Headings are short (`Ch`, `Prog`, `Trans`, `Vel +/-`) so the columns sit close, the buttons are evenly spaced, and Input and Output grow with the longest port a track names, up to 24 characters (revised November 2026 after use), with three blank cells between them. The piano roll's grid and a new note's length and velocity were columns too for a while, and went back to the piano roll, whose status line and inspector show them, as they only matter there. Mute, Solo, Arm, Thru, Chase and Q sit immediately after the name, as `M`, `S`, `R`, `T`, `C` and `Q` buttons (revised November 2026 after use; see Recording in the GUI for how the buttons show). Numeric columns and their headings align on the right, with two blank cells after Time offset so its values don't run into Quantise's. Transpose is in semitones and time offset is explicitly musical or in milliseconds; these and velocity offset affect playback without changing the stored notes. Playback quantise is a track setting. Chase starts notes already held when playback begins partway through them; it belongs to each track, so it is a column alongside Mute/Solo rather than a global status-bar control. The inspector explains it when that column is selected. Enter toggles each button in the table, with selected rows following the cursor's, and `track-mute-toggle` (`M`), `track-solo-toggle` (`S`) and `track-chase-toggle` (`, t c`) toggle the current track from any view that has one. On a selection in the Tracks view, `tracks-mute-toggle`, `tracks-solo-toggle` and `tracks-chase-toggle` (the same keys) act as Enter does. The Name column grows with the longest name, up to 32 characters or as far as the table still fits the window, and the bar above shows a name whole (revised November 2026 after use). Arm and Thru are described under Recording in the GUI. There is no whole-track Loop column: looping belongs with the section and cycle designs.
- **Editing.** Follow the event list: `j` / `k` move between tracks, keeping the selected column, `h` / `l` move between fields, Enter edits in the cell (revised November 2026 after use, from the inspector; the inspector now holds only what the table has no room for, such as a long name, a track's program changes and warnings), and Tab/Shift-Tab commit and move between editable columns. The numeric increment/decrement commands step values. Space remains transport. `gr`, `ge` and `ga` open the selected track in the other views, keeping the remembered musical position, and Backspace returns. The view is also offered through the Views menu and command palette. Selecting several rows allows a property to be set on those tracks together; event-deletion keys must not silently become whole-track deletion. Edits are undoable and saved with the song. `gt` and `, v t` open this view; a count on `gt` chooses the track (`3gt`). Ctrl-PageDown / Ctrl-PageUp replace `gt` / `gT` for next/previous track; `]t` / `[t` remain planned for takes. `V` selects complete track rows for copying or property edits. Enter sets the selected field to an absolute value on every selected track, except names, which are edited individually. Steps change each track relative to its own value; an invalid value refuses the whole batch. Each batch is one undo step. Visual `p` / `P` replace the selected tracks as one undo step. Delete whole tracks explicitly with `V` then `d`; Normal-mode event deletion does not delete tracks.
- **Bank and program setup (decided November 2026).** A track has an optional bank-select MSB, bank-select LSB and program, each numeric, 0-127, and set or unset on its own; unset leaves the choice to the instrument or the song's events, and is distinct from zero. A bank with no program is valid, for songs whose own program changes choose the sound. Program numbers follow the event list's 0-127; an instrument that counts from 1 will get its own setting with the instrument tables, rather than a global one. They are columns of their own, MSB, LSB and Program, `-` when unset (revised November 2026 after use, from a single Program column with the banks in its inspector). A `•` in the cell means the track has program changes of its own, and the inspector says how many and where the first is. Tracks on the same port and channel with different setups are allowed, the last sent winning, but the cell takes the warning colour and the inspector names the others. The track bar shows a setup when set, in every view that has that bar.
- **Reordering tracks (decided November 2026).** `, t o` is the way to find it, and starts a mode for moving a track or block as far as it needs to go, seen as it goes, ending in Enter or Escape; Alt-Up and Alt-Down are the quick way, moving at once with no mode. A mode that takes nothing else is simpler and safer than leaving transport or editing working partway through a move, so every other key does nothing. Moves are real edits while they happen, so every view shows them, merged into one undo step; Escape moves back, which leaves no step, though like any edit it ends what could be redone. In the mode, keys are read directly rather than through the key map.
- **Choosing a port (decided November 2026 after use).** A port is chosen from those detected, in a list at the cell of up to eight rows, narrowed by typing, since a name had to be remembered and anything at all was accepted. Typing narrows it, so Up and Down move rather than `j` and `k`. A port that wasn't found stays set, as a song may come from another machine or an instrument be unplugged: dim in the table, in the warning colour in the inspector, and marked on the list.
- **When a setup is sent (decided November 2026).** Once at each playback start, before any count-in, not on each pass of a loop, as bank MSB, bank LSB then program, ahead of the chased values. So a later program change of the track's own overrides it, and finds the bank the setup asked for, which is why a setup is sent even if the track has program changes. An edit sends it at once, while playing or stopped, so a sound can be tried, unless the track's own program change is already in force during playback: it then waits for the next play, and the status line says so. Opening a song or drawing a view sends nothing, and neither does a muted track, until it next becomes audible. Later, reusable program tables for particular instruments can give names alongside or instead of the numbers; numeric addresses remain the underlying values.
- **Playback quantise (decided and built November 2026).** A track can play its notes quantised, stored where they were played, by the quantise transform's rules and settings: a grid (the track's editing grid until set, independent of it once set), strength, swing and what moves (starts, ends, both or lengths), with its pedalling following its notes and other controllers left in place, so Freeze, committing it, will give what was heard. It works in the track's bars, before both kinds of time offset, so a deliberate push or drag still applies; the metronome and thru are unaffected. A `Q` button beside Mute, Solo and Chase turns it on and off, keeping the settings, as `, t q` does from any view with a track, and a `V` selection follows the cursor's row. The Quantise column summarises the settings, dim while off; Enter there edits them in the inspector, the one column that does, as it holds four: Tab goes between Grid, Strength, Swing and Moves, Up and Down step each (the grid through the straight and triplet lengths from 1/1 to 1/64, strength by 5%, swing by 1%, what moves in turn), and each change is heard at once and is its own undo step. Of two notes of a pitch that would start on one line, the one that would move further stays where it's stored, and the rest of the track is quantised; its inspector says how many were left so (revised November 2026 after use, from playing the whole track as stored, which on a coarse grid most tracks did). A pedal that would pass the next of its pedal still leaves the track as stored. `, T q` bypasses it for the whole song, to compare, saying so in the status line, and isn't saved. The piano roll faintly marks where a quantised note will be heard when it's more than a few ticks from where it's stored, `, T m` (the `quantizemarks` setting) hiding the marks; the event list shows stored times. A change made while playing takes effect from the playhead: a note already sent by the old timing isn't sent again though the new one puts it ahead, and one the new timing puts behind the playhead isn't heard until the next pass, as with any edit there.
- **Shared columns, future configuration.** Define track columns separately from a view's layout, with stable identifiers and shared formatting and editing commands. Keep the default order in one ordered list that drawing and field navigation both follow, so changing the order in code is straightforward and does not change a column's identity. Both the Tracks view and arrangement read the same track properties, so a mute or solo edit has the same meaning wherever its column is shown. Each view chooses its own visible columns; later, `modalrc` can configure visibility separately for the two views, including mute and solo beside the arrangement's track names. Column configuration and instrument program tables are future work, not requirements for the first Tracks view. Their file syntax and formats are not yet chosen; whether users can also configure column order remains an open question.

- **Freeze (decided November 2026).** `, t f` or `:track-freeze` opens a list: All, Transpose, Velocity, Quantise and Time offset, with All selected initially. Up/Down choose any entry, including dimmed ones, stopping at the first and last entries. Enter applies an available choice; on a dimmed choice it does nothing, shows no status message and leaves the list open. Escape cancels. Unavailable choices stay dimmed with their reason, which is their only explanation in the menu (navigation and confirmation revised after use, November 2026). A colon argument chooses directly: `:track-freeze quantise`, or `all`, `transpose`, `velocity` or `time` (`quantize` and `offset` also work); a refused direct command still reports its reason. Freeze acts on the whole current track, including a muted track, or a `V` selection of rows in Tracks; event and time selections are refused. Playback must be stopped, including its pending stop acknowledgement. A batch validates every track against the original song before changing any, and freezes as one undo step, restoring events and settings together on undo.
  - The list validates the complete result of each choice before offering it, including pitches outside MIDI range, starts before zero, rounding collisions and collapsed notes. Invalid choices are dimmed with their reason. A choice is also dimmed with "Nothing to freeze" if no selected track has that playback transform active; All is dimmed if none has any active transform. Zero offsets, including musical zero, are inactive; retained parameters with quantise off are inactive. One unchanged row does not disable a choice that has work on another selected row, but a refusal on any row disables the entire choice. Enter and direct colon commands use the same validation and check again before changing anything (refined after the first UI trial, November 2026).
  - Apply all playback transforms, or just the one chosen. Transpose affects notes and polyphonic pressure; velocity offset affects note-on velocity, clamped to 1–127 as in playback, leaving release velocity alone. Quantise uses playback's exact rules, including pedalling, notes left in place after a clash and the stored-timing fallback when pedals would reverse, reporting the latter two. Time offset moves every track event, including text; for notes it moves both ends. Apply quantise before time offset. Playback and Freeze share their pitch, velocity and quantise functions.
  - Reset only the chosen transforms: transpose and velocity offset to zero, time offset to zero, and enabled quantise to off while retaining its parameters. Inactive quantise stays off and keeps its parameters. Bank/program setup, routing, mute/solo, chasing, meters and editing defaults are retained.
  - Transpose and velocity can be frozen independently. Quantise can be frozen while keeping time offset live. Time offset alone is unavailable while quantise is enabled: "Freeze quantise first, or choose All", since moving stored notes before quantising can change their destination grid lines. Quantise and All are unavailable while global bypass affects an enabled quantise on a chosen track; transpose and velocity remain available.
  - Refuse the entire batch if a pitch would leave 0–127 or a start would precede tick zero; neither discard nor clamp these events. Events can cross section boundaries: their new starts determine ownership, notes sustaining across boundaries stay whole, existing section boundaries remain, and the final section grows when needed.
  - Musical offsets are exact tick shifts. Millisecond offsets use the current tempo map, rounding each start and note end independently to the nearest tick in elapsed time, ties earlier. Refuse a positive note rounded to zero length or a newly introduced collision; preserve existing imported overlaps and zero-length notes. Freezing milliseconds captures the current tempo map: later tempo edits can change the elapsed-time displacement that was frozen.
- **Whole-track copying (decided November 2026; part of the first implementation).** Copying rows preserves settings and all of a track's section content, including its own meters and editing defaults. Extend the register to hold this separately from event contents. `V` selects complete track rows, `y` copies them (`Vy` this track, `Vjy` this and the next), and Normal-mode `p` / `P` insert new tracks after / before the current row. Each copy gets a new track identity and an appropriately numbered name; the song's section structure and conductor are shared. Keep output routing, channel, mute and solo as copied: an audible copy may send duplicate notes to the same destination, and the user chooses how to route or mute it. A muted, non-soloed copy can serve as a backup or alternative without a separate backup command. `yit` in the editing views continues to copy event contents. Visual `p` / `P` replace the selected rows. Named registers work too, and appending adds tracks as rows. The initial implementation requires matching PPQN, section names, order and lengths; otherwise it refuses the paste without changing anything. General mapping across different song or section layouts is deferred. Marks are not duplicated, since a mark letter names one place.
- **Offset units and timing display (built November 2026).** An Offset value retains either elapsed time (milliseconds) or musical time (ticks, with note fractions accepted as input). Accept a musical value with a signed fine-tick adjustment, such as `+1/16-22t` or `-1/16+22t`, using ordinary signed addition and subtraction. At 960 PPQN these are +218 and -218 ticks respectively; each is one musical offset. A musical offset keeps the note fraction and fine ticks it was given in as well as its total, so the Tracks table and song files show `+1/16-33t` as typed, and plain ticks as plain ticks; millisecond values keep `ms`. Fine steps change the fine ticks, grid steps the fraction, and a change of PPQN keeps the fraction and scales the fine ticks (revised November 2026 after use). The unit is part of the setting's meaning, saved with it: a fixed millisecond offset remains constant as tempo changes, while a musical offset follows tempo. Changing a display format alone must not convert between these behaviours. Musical offsets can be frozen as tick shifts without depending on the current tempo map; millisecond freezing involves tick rounding and remains tied to that map. The inspector uses a musical display of bar, a position in a chosen note unit, and a signed tick remainder, with lengths shown as a count of those units plus a remainder. Keep the exact bars:beats:ticks representation readily available; the event list can retain that compact format initially. The selected display unit must be visible and can be fixed or follow the editing grid; changing units reformats the same data without snapping notes. Coarse and fine components are separately editable: adjusting the coarse value preserves the fine adjustment, and adjusting Fine changes ticks. The inspector has the Note heading above Pitch, Velocity and Off Vel on the left; Start, Length and Ends each have a row to their right across coarse, fine and exact values, under Units, Fine(t) and B:B:T. Fine values are right-aligned, and the exact values' colons line up, with a beat column two wide only if the track has a meter of more than nine beats (revised November 2026 after use). Elapsed time is in the bar above. `e` edits the inspector in both the piano roll and event list; Tab follows the rows; Up/Down step, Enter commits and Escape leaves. Start and end steps count from one within the bar the time falls in, length steps from zero. Fine is the signed distance from the nearest step (ties use the earlier step), and its entry is absolute, with an optional `t` suffix. `timingunit=grid` is the default; a fixed note fraction such as `timingunit=1/16` only changes the display. Rounded units at a low PPQN are labelled. Track offsets are limited to ±1000 ms or ±64 whole notes (agreed November 2026). In the table, `=` / `-` and Ctrl-A / Ctrl-X step a musical offset by the track grid, `+` / `_` by one tick; millisecond offsets step by 1 ms. Note timing entries are bounded to ±1000000 for safe arithmetic; steps from one must be positive and lengths must remain positive.

  The [Sequencer Plus Gold v4 manual](https://www.scribd.com/doc/251057467/Sequencer-Plus-Gold-Manual-v4), Main Screen p. 44 and Note Edit p. 82, describes track offsets in quarter notes and clicks, with direction arrows; note starts use the selected note unit and a signed click adjustment. This is reference material for the display discussion, not a decision to copy its notation.

- **Song tempo (open question, November 2026).** Consider a visible song-tempo control and whether there should be a default used in the absence of explicit conductor tempo changes. Currently a tempo map always starts at tick zero (120 BPM in a new song), and each section explicitly stores its starting tempo. A separate fallback would therefore need rules for inherited versus explicit section tempos; changing a single initial value must not unexpectedly leave later sections at the old tempo. Consider exposing the conductor's tempo through a convenient song control before introducing another source of tempo. This question is separate from the first Tracks view implementation.

Track settings, numeric bank/program setup and playback quantise share the track model and column definitions. Their historical implementation sequence is recorded in decisions.md.

**Piano roll pages (decided October 2026, revised after use).** The piano roll shows a width of a whole number of bars at a time, usually starting at a bar line, rather than a freely zoomed timeline; but it can be scrolled to start anywhere.

- The bars in view together are stretched to fill the window width, whatever their length: a one-bar page of 7/8 is as wide as one of 4/4. Within the view, time keeps one scale, so on a page mixing meters a 7/8 bar is a little narrower than a 4/4 bar. Off a bar line, the view runs from where it starts to the same place that many bars on, except while it's scrolled (below).
- **Opening a track** (Enter on a bar in the arrangement, coming to the piano roll at a time outside its view, or Ctrl-PageDown / Ctrl-PageUp) shows whole bars, in pages that restart at each section (decided October 2026, rather than at each label): with a section starting at bar 3, 4-bar pages show bars 3–6, 7–10 and so on. The view is always the full number of bars, so a page near a section's end runs on into the next section rather than stopping short.
- **Turning:** when the cursor moves past either edge, the view turns by its own width, keeping where it starts in the bar (a view from bar 3 beat 3 turns to bar 7 beat 3), so turning never jumps. Following the playhead turns it the same way.
- **Scrolling (decided October 2026):** `zz` centres the view on the cursor in time as well as in pitch (as Vim's centres the line), keeping the number of bars, so partial bars may show at either edge. `Ctrl-h` / `Ctrl-l` move the cursor by grid steps and scroll the view with it, so the cursor stays put on screen; `Ctrl-{` / `Ctrl-}` do the same by a bar, keeping the cursor's place in the bar, the view moving as far as the cursor does (bound as Ctrl-Shift-`[` / `]` too, the way most keyboards send them; in the arrangement they scroll by bars, as `Ctrl-h` / `Ctrl-l` do there). While scrolled, the view keeps its length in time, so its scale stays put as bars of another length come and go (decided October 2026, after use: fitting the bars at each step made the view stretch and shrink, and the cursor jump); turning, zooming and opening a track fit whole bars again. The view never starts before bar 1, but may show time past the song's end, with the end marked, so `zz` can centre there. `Ctrl-Shift-h` / `Ctrl-Shift-l` (or with the arrow keys; `scroll-page-left` / `scroll-page-right`, decided October 2026) scroll by a page the same way, the view's length in time, as turning does, the cursor no further than the song's start or its last step; in the arrangement, by as many of the cursor's track's bars as are wholly in view, since its cursor is a bar. Refused on the section strip.
- **Zooming:** `zi` / `zo` change the number of bars in view, stepping through a list: 1, 2, 4, 8, 16 by default, configurable later (e.g. `set pagebars=1,2,3,4,6,8,12,16`); a count setting the size directly (`3zp`) is to come. Zooming keeps the cursor at the same place across the view (decided October 2026, after use, rather than anchoring on the bar line nearest the cursor and returning to whole bars, which left zooming out and back in at a different place): with the cursor halfway across 4 bars, zooming out to 8 keeps it halfway, so zooming back returns to the same view, except where the view would start before bar 1 and stops there instead. `z0` goes back to the default number of bars as whole bars, the section's page holding the cursor.
- The view's bar shows the section the cursor is in and the bars in view, partial ones included (`Bars: 8–12`), rather than a page number, since the view needn't be one of the section's pages.
- Vertically, the view scrolls (unlike horizontal paging) to keep the cursor's pitch visible; when a track opens, the view centres on the track's pitch range.
- Grid lines are drawn at the current grid, with beat and bar lines stronger. A grid coarser than a beat is drawn as itself, its steps as beat lines and the beats between left out (decided October 2026, after use: drawing the beats as well made a grid of 1/2 or 1/1 look like one of 1/4). If the grid is too fine to show legibly across the page, lines are drawn at the finest level that fits; movement still uses the real grid. Notes are always drawn at their exact positions, so recorded material never looks falsely quantised.

**The piano roll screen (decided October 2026)**

```
 NOTE  21:2:480 │ E2 (40) │ vel 96 │ len 1/8 │ ch 1 │ Bass          ← inspector
 Chorus · bars 21–24 · page 2/4                     grid 1/16 │ len =grid
──────┬─────────────────────────────────────────────────────────────
  G2  │ ·           │           ·           │                        ← pitch rows
  F#2 │▒            │                       │                        (black keys shaded)
  E2  │   ████      │  ██[██]       ████    │
  D2  │             │        ███            │
  ...
──────┼─────────────────────────────────────────────────────────────
  vel │ █  █  █     │  █ [█]  █     █       │                        ← controller lane
──────┴─────────────────────────────────────────────────────────────
 NORMAL │ 21:2:480 │ ♩120 │ E minor │ scale lock │ ...                ← status line
```

From the top: the inspector (the current note's details, or the cursor's position and pitch on an empty spot; `e` enters it); the page header (section, bar range and the cursor's place); the keyboard column of note names, with black-key rows shaded across the full width; the note area, the page's bars stretched to the width; the controller lane; and the status line.

- **Notes** have a distinct start (a bold first cell) and lighter sustain, so repeated notes of one pitch read as separate notes. Brightness follows velocity, so dynamics show in the note area as well as the lane. Off-grid notes are drawn at their exact positions, inside cells. The current note is in the accent colour, selected notes in the selection colour, ghost notes dimmed.
- **The cursor** is a crosshair: its cell highlighted, with a faint highlight along its row and column, so both its pitch and position read at a glance.
- **Scale lock** shows as in-key rows slightly brighter and out-of-key rows dimmer, so out-of-key notes stand out.
- **Rows:** the number of pitch rows follows the window's height (see Piano roll pages for scrolling and `zz`).
- **Hearing it:** optional audition plays each note as the cursor lands on it (useful when stepping with `Tab`); Space plays from the cursor, `, L` loops the page or section, and the playhead is a vertical line, with pages turning by themselves when follow is on.

**Ghost notes.** Other tracks' notes shown dimmed behind the current track's, for writing a part against others. They can't be edited and the cursor ignores them. Choosing them is quick: `]g` / `[g` show the next / previous track as the ghost, one at a time, with no setup; `, g` opens a hint menu of tracks with number keys (`1 Drums ✓  2 Bass ✓  3 Pad`), where numbers toggle tracks and `Esc` closes it; `, v g` shows or hides the ghosts without forgetting them. Each track remembers its own ghosts, saved in the song (the keys track always ghosting the bass, say).

**Split view.** Other tracks in panes of their own, locked together in time, with Vim's window keys: `Ctrl-w s` opens another track in a pane above or below, `Ctrl-w j` / `Ctrl-w k` move to the pane below / above, Ctrl-PageDown / Ctrl-PageUp change which track the focused pane shows, `Ctrl-w c` closes it and `Ctrl-w =` evens the heights. Every pane shows the same bars and turns pages together; pitch scrolls in each on its own. Every pane can be edited; the focused one has the cursor and drives the inspector. More than two panes are allowed (drums, bass and keys stacked). Ghosts are for how one line sits against another, splits for writing interlocking parts.

**Controller lanes.** The lane shows velocity by default; `, v c` switches it to a chosen CC (CC 1, say), pitch bend, aftertouch or sustain. A track's own program changes are marked in the ruler instead, not being a curve: `◆` and the number, in the `event-sign` colour, the number giving way where the next sign leaves no room (decided November 2026). A setup isn't marked, not being an event in the song. Velocity, sustain, CC 1 and pitch bend get good default support first; several lanes at once can come later. `gl` moves the cursor into the lane, where `h` / `l` go to the previous / next note or event, `k` / `j` raise and lower the value, digits and `Enter` set it, and `Esc` goes back to the notes. Operators and transforms work on lane values over motions and selections (a velocity ramp over a selection). A search's matching controllers are highlighted in the lane, each event in the match colour, as matching notes' velocities are (to do with the lane's controllers, noted November 2026; see Search in decisions.md).

**Switch controllers.** Controllers that are really on or off (sustain, sostenuto, soft, legato and portamento switches; the set is configurable) are regions, not curves: the lane draws pedal-down spans as solid bars, like notes, just under the note area, and they're edited like notes, with `Tab` / `Shift-Tab` to the next / previous region, `o` to put the pedal down at the cursor (for the default length, or up to the next region), `=` / `-` to lengthen and shorten by a grid step, `Alt-h` / `Alt-l` to move earlier and later, and `x` to delete. Down and up are the only states, so there's no dragging values. Recorded and imported values of 64 and above are down, below 64 up; half-pedal values are kept, and shown in a lighter shade, but edits treat a region as one unit. The pedalling tools are in MIDI transforms.

**Drum maps.** A track can have a drum map, a name for each note number: General MIDI by default, or a custom map, chosen per track and saved in the song or as a reusable map file. With one, the keyboard column shows names (Kick, Snare, Closed HH) rather than note names, the inspector shows the name beside the note number, and `gp`, search, `:select pitch` and the palette take the names (`gp kick`, `/snare`). Drum tracks start with scale lock off.

**Folding (agreed design).** show occupied pitch rows (in the track, or optionally the section), named drum-map rows even if empty, or their union, so a drum track shows a useful set of rows rather than 128. The proposed toggle is `, v f`; mode controls are still to decide. With folding on, `j` / `k` step between the rows shown, and so does extending a `V` selection. For example: fold a drum track, put the cursor on Kick, `V`, and adjust.

**The section strip (decided October 2026)**

```
           │1   5   9   13  17  21  25  29
 SECTIONS  │Intro  │Verse 1        │Chorus         │Verse 2 ...
───────────┼───────────────────────────────────────────
 1 Drums   │░░░░░░▒▒▒▒▒▒▒▒▒▒▒▒▒▒▓▓▓▓▓▓▓▓▓▓▓▓
 2 Bass    │      ▒▒▒▒▒▒▒▒▒▒▒▒▒▒▓▓▓▓▓▓▓▓▓▓▓▓
```

A row above the tracks in the arrangement, showing each section's name across its span in its colour; section boundaries are faint lines down through the tracks. `k` from the first track moves up onto the strip, `gs` jumps to it from anywhere in the arrangement, and `j` returns to the track the cursor came from, at the same position. On the strip the cursor is a whole section, and the inspector shows it: name, bar range, length, meter, takes and cue slot. `h` / `l` go to the previous / next section and `0` / `$` the first / last, with counts.

Sections behave like lines in Vim:

| Key | Effect |
| --- | --- |
| `x` | Delete the section under the cursor; later material closes up |
| `Y` | Yank the section under the cursor |
| `d` + motion | Delete sections over a motion (`dG` deletes to the last) |
| `y` + motion | Yank sections over a motion (`y2l` yanks this and the next) |
| `p` / `P` | Put the yanked sections after / before this one |
| `Alt-h` / `Alt-l` | Move the section earlier / later, swapping with its neighbour |
| `J` | Join with the next section |
| `=` / `-` | Lengthen / shorten the section by a bar (later material ripples) |
| `i` / `a` | Insert a new empty section before / after this one, then ask for its name |
| `c` | Rename it (focus goes to the name in the inspector) |
| `e` | Edit any of the section's fields in the inspector: name, colour, length, cue slot |
| `.` | Repeat the last operation |

- `d` and `y` stay operators taking motions, as everywhere; `x` and `Y` are the single keys for the section under the cursor, and `dd` and `yy`, which are a bar elsewhere, are refused here, pointing to them (decided October 2026). Counts apply (`3x`, `2Y`). A section that moves takes the cursor with it, and each operation is one undo step. Duplicate a chorus to the end with `Y`, `$`, `p`; move the bridge two places earlier with `Alt-h`, `Alt-h`.
- `V` selects a run of sections, for `d`, `y` and `Alt-h` / `Alt-l` to act on the block, and `, L` to loop it.
- `Enter` plays from the start of the section, `Shift-Enter` cues it during playback, `, L` loops it and `:cue F3` gives it a cue slot.
- Splitting is done from the tracks (`:section-split NAME`), where the cursor has an exact bar position; the strip works on whole sections.
- **Decided for milestone 5's strip.** Shortening a section with `-` deletes everything starting in the bar that goes, as `d` over it would (undo brings it back), and never shortens below a bar. A new empty section from `i` / `a` is 4 bars, or the count (`8a`). New sections are named `Section` and one more than the highest number among sections named that way, so they count up in the order they're made even when that leaves gaps; any name stays unique, numbered if another section has it ("Chorus (2)"). `i` / `a` then open the `:` prompt with `section-rename` and the new name, to type over or keep with Enter, and `c` does the same for the section under the cursor; `e` edits its name and length in the inspector (see Inspector). Yanked or deleted sections go in the one unnamed register, as Vim keeps characters and lines in one; `p` with bars in it on the strip, or with sections in it on the tracks, says what it holds rather than guessing. Until sections can be given colours, neighbouring sections on the strip alternate between two shades. A song always keeps at least one section, so deleting every one is refused. As built: the strip is the fourth row above the tracks, after the labels' names, the meters and the bar numbers; section names moved there from the ruler, which now names labels only. `section-strip` (`gs`), `move-left` / `move-right` (`Alt-h` / `Alt-l`), `join` (`J`), `insert-before` / `insert-after` (`i` / `a`), `change` (`c`), `register-put-before` (`P`) and `yank-line` (`Y`, as `yy`) are commands of their own, which other views refuse until they have a use for them; `+` / `=` and `-` step a section's length, as they step a field in the event list. `section-rename NAME` renames the section at the cursor from any view. Without a name (decided October 2026), `:section-rename` opens the prompt with the section's name to edit, as `c` does, and `:section-split` splits first, naming the new section `Section` and a number, then asks the same way, as `i` does, so Escape keeps the name. Deleting or yanking sections puts them in the register, and the strip's operators work as on lines: `dd` and `x` this section, `d2l` this and the next, `d$` to the last. (Revised October 2026: `dd` and `yy` are refused on the strip and `0` / `$` only move, so the last is `dG`; see Ranges, objects and putting in decisions.md.)

**The outline view (decided October 2026)**

A vertical list of the song's sections (`, S o`), for the running order of long songs with many sections, which is also the cue sheet:

```
     ▶  1  Intro          1–4     4/4   F1
        2  Verse 1        5–20    4/4   F2
     ◆  3  Chorus        21–28    4/4   F3   2 takes
        4  Instrumental  29–52    7/8   F4
```

Columns: number, name, bar range, the conductor's meter, cue key and takes (later, linked sections and repeats, e.g. "Chorus ×2", like an MPC's song mode). Its keys are the strip's, turned upright: `j` / `k` the next / previous section, `Alt-j` / `Alt-k` move the section down / up the running order, and `x`, `Y`, `p`, `P`, `J`, `i`, `a`, `c`, `e` and `.` as on the strip. `Enter` / `Shift-Enter` play from or cue the section, `Shift-F1` to `Shift-F12` assign that cue slot, `F1` to `F12` cue the section assigned during playback, and `Esc` or `, S o` go back. While playing, `▶` marks the section playing and `◆` the one cued next, so the outline doubles as a performance view. Later, a setlist view one level up could list songs the same way (see Feature notes: live rig mode).

**Resizing.** Text size stays fixed when the window resizes; the grid gains or loses cells. In the arrangement and event list, extra columns show more time at the same zoom (the piano roll instead stretches its page of bars to the width), extra rows show more tracks or pitches, and panels such as the velocity lane keep fixed heights while the main area takes the rest. `Ctrl-+` / `Ctrl--` change the font size, and with it the cell size. So that resizing is smooth rather than jumping a cell at a time (decided in milestone 3), regions are laid out in pixels: bars at the top are anchored to the top edge and bars at the bottom to the bottom edge, so they follow the window edge a pixel at a time, and right-aligned status segments follow the right edge. The main area takes everything between, including a partly visible last row and column, clipped, which are revealed gradually as the window grows. The cursor and scrolling count only fully visible rows and columns, so the cursor never sits on a half-hidden one.

**Grid regions and bars (decided in milestone 3).** Only the views you move around cell by cell (event list, arrangement, piano roll) are grid regions, laid out in cells. The bars (status line, inspector, command line, hint menu) aren't navigated as a grid, so they're laid out as segments of text at pixel positions instead:

- **A terminal look.** Bars use the same font and theme colours as everything else, with no bevels, gradients, borders or OS-style controls: a bar is a line of text on a theme-coloured background, like a Vim status line, so it blends in.
- **Groups anchored to edges.** Segments flow left to right in a left, centre or right group. The left group is anchored to the left edge, the right group to the right edge (so it follows the window edge a pixel at a time) and the centre group to the centre. Each segment keeps its own colours and attributes, and the bar's background fills its whole width.
- **Padding.** A margin between each group and its window edge (half a cell's width by default) and a minimum gap between groups (two cells by default), as settings.
- **Too little room.** The right group is kept whole, and the left group gives way: its last segment is cut short with `…`, and a segment that can't show at least a few characters is dropped. If the right group alone doesn't fit, it is cut from its left end the same way. Per-segment priorities can come with the configurable status line (see schedule.md).
- **Fields without a grid.** Segments can be focusable fields, so `Tab` moves between the inspector's fields without a grid underneath.
- A bar is one line of text high, plus padding, and is anchored to its window edge (see Resizing). Bars that aren't text, such as the piano roll's ruler, are pixel regions that stretch with the width.

**Minimum window size (decided in milestone 3).** The window can't be dragged smaller than 120 × 30 cells (80 × 24 at first; raised in milestone 4, when the inspector's fields and the track's bar needed the width, to near the size Modal opens at), a setting (`set minsize=120x30`) that follows the font size: if a larger font puts the window below the minimum, the window grows to fit, as far as the screen allows. The default bars fit at the minimum, so the overflow rule above is a safety net for long content (a long track name, a message) rather than a routine sight.

Splits (later): two views side by side, e.g. arrangement above event list, as with Vim windows.

**Inspector**

- **As built in milestone 4.** Every view has the same order from the top (decided in milestone 4): the view's own bar first, as a title, then the inspector, then the view. The event list's bar labels its values, `Track 1: Bass   Channel: 1   Output: Pro-800 ... Section: Section 1   Bars: 1–8` (`Port:` until 11 November 2026), labels dim and values in the text colour; the piano roll will have a bar of its own like it. The inspector is a panel of two rows on a tint of its own (the `panel` colour), so it doesn't read as another bar: the kind of row (Note, CC, Section…) in the accent colour, then each property's heading, dim, above its value, with a quarter of a line's padding above and below. Each column has a fixed width, as wide as its longest value can be (a position as wide as the song's last, a length 15 characters, a controller 25), so the columns stay put as the cursor moves from row to row. It shows what a row can't: a note's end as well as its length, a controller's standard name (`74 Brightness`, from a table in the core the piano roll's lanes and the palette will share), text and SysEx whole, and the time from the song's start (`1:02.250`). The track and channel are left to the view's bar, until a view shows several tracks at once (the arrangement, a split piano roll), when the inspector shows them too. On a row that isn't an event it says what the row is: a section's bars and length, a tempo in BPM and milliseconds per quarter (`594.059 ms`, exact to the microsecond the tempo is stored in, which as a raw number was hard to read), a meter, a label, or at the end the song's length in bars and time. The bar stays separate from the inspector, so the piano roll can use the same inspector. Half a line of space separates the bar, the inspector and the list, rather than boxes or rules that cost whole rows. The view itself is the one area on the `background` colour; everything around it, the gaps included, is on the `chrome` colour, which the built-in themes make the bars' own colour (decided in milestone 4). So the view bar and the gaps run together as one strip rather than stripes, the inspector sits in it as a block of its own, and the view stands out as darker in the dark theme and paler in the light one. A chrome halfway between the background and the bars was tried, and left the bars looking like stripes. The status line ends with the song's file, `song.mid (imported)` for an imported MIDI file (which saving doesn't write over), or `No file`, and `[+]` while it has changes not saved, as in Vim.

Inspired by SPG's note information area, a strip at the top of the window always shows every property of the event under the cursor, in every view. For a note: position, note name, MIDI note number, velocity, duration, release velocity, channel and track. For a CC: controller number and name, value, channel.

```
 17:2:480  │  E3  (52)  │  vel 96  │  dur 0:1:240  (1/8.)  │  rel 64  │  ch 1  │  Bass
```

- **Edit fields from Normal mode.** `e` moves focus into the inspector; Tab and Shift-Tab move between fields; Enter confirms and Escape cancels, returning to the note.
- **Jump straight to a field.** Inside the inspector, a single letter jumps to its field: `p` pitch, `v` velocity, `d` duration, `c` channel.
- **Flexible input.** Pitch accepts a name or a number (`F#3` or `54`); duration accepts a note fraction (`1/8.`, `1/16t`) or ticks; any number field accepts a relative change (`+10`, `-5`) and `Ctrl-A` / `Ctrl-X` to step it.
- **Works on selections.** With several events selected, each field shows the common value or a range (`vel 64–90`); typing a value sets all of them, and a relative change adjusts each one.
- **Configurable.** Which fields appear, their order, and whether the strip sits at the top or bottom are set in the config file, like the status bar.
- **As built in milestone 5 (October 2026).** `e` (`inspector-edit`) edits the inspector's fields in the piano roll (the current note's position, pitch, velocity, length, end and release), and on the section strip (the section's name, and its length in bars or a change, `+2`); on a track in the arrangement it says what it edits elsewhere, and on an empty spot in the piano roll that there's no note. Each field is typed into as the event list's cells are, boxed in place of its value. Tab and Shift-Tab set the field and go on to the next or previous, round from the last to the first; Enter sets it and leaves; Escape leaves it as it was, fields set before staying set; Up and Down step it straight away where it can be stepped (velocity and values by 1, pitch by a semitone, position by a beat, length and end by a 1/16, a section's length by a bar). Each field set is an undo step. A value that can't be set keeps the field open with the message, as in the event list. `e` opens on the field it was last on in that view, since going through notes changing one property is the common case. A note's end can be typed (decided October 2026, after use: an end is sometimes what's known), and sets its length. The single letters jumping to a field are left out, since typing replaces the value and pitch names are letters; Alt and a letter may come later. Time, which follows from the position, is set aside at the inspector's right, its value dim, in every view (decided October 2026). A value is bright where `e` can edit it and dim where it can't, so the inspector shows what `e` will edit: dim on an arrangement track and on an empty spot in the piano roll, and on the strip all but the section's name and length. The event list now marks its editable inspector fields bright too (changed November 2026 with coarse/fine timing). Several events at once wait for Visual mode. In the event list, Enter edits the cell under the cursor in place, while `e` opens the inspector for track events, including the coarse/fine timing row (changed November 2026). On conductor rows, `e` retains cell editing. The same navigation keys work in both editors: Tab and Shift-Tab set the field and go on, wrapping round, and Up and Down step it. While a value is being edited it sits against the right of its box, as a spreadsheet cell's does, going back to the left once set (decided November 2026, after use).

## Customisation

Themes, key bindings and the status bar are all defined in a plain-text command file from the start, so the defaults are just shipped configuration. The file uses the same command language as the `:` command line: every command a file takes can be typed there, and the prompt runs any other command too (see The command registry in use). It can be re-run with `:source` without restarting.

```
" ~/.config/modal/modalrc
set pagebars=1,2,4,8,16
set theme=dusk
nmap q quantize
nmap Q macro-record
leader , x i  invert         "Invert"
leader , x T  transpose-key  "Transpose in key"
highlight cursor      #e0af68
highlight cursor-text #1a1b26
statusline left=mode,position,tempo right=key,loop,midi-in
```

The command language stays flat: no variables, conditionals or loops. If programmability is ever needed, it comes as a separate scripting language (Lua), not by growing the command syntax.

- **Themes.** Colours are assigned to semantic roles (cursor, selection, playhead, note, muted track, velocity bar, label, status segments), never hard-coded in views. Light and dark themes ship by default; users add their own. A field free text is typed into (a track's, section's or port's name, a text event's words) sits on the `field` colour, filling its width, so it shows as a field even when empty (decided November 2026).
- **Key bindings.** Per-mode bindings and leader sequences, rebindable like Vim's `map`. Each binding names a command and a hint label for the leader menu. Commands are named in lower case with hyphens, by what they act on: `cursor-left` moves the cursor, so a command moving notes left can't be mistaken for it (decided in milestone 3). The modes are Normal, Visual, Insert, operator-pending and command line. The defaults aim for stable muscle memory and won't be reshuffled between versions. Commands come from the command registry (see Architecture).
- **Config files (decided in milestone 3).** The user's command file is `~/.config/modal/modalrc` on Linux and `%APPDATA%\Modal\modalrc` on Windows, found through the platform layer. The shipped defaults (a default command file and the light and dark themes) are built into the program, so it runs with no files installed; the user's file runs after them. `set theme=NAME` starts again from the dark theme, then runs `themes/NAME` from the config directory, or else the built-in theme of that name, so a theme of your own need only set the colours it changes; `highlight` lines after it override single colours. The built-in files are ordinary command files in the repository (`assets/config/modalrc` with the default key bindings, `assets/themes/dark` and `light`, after Tokyo Night and Tokyo Night Day), built into the program. An error reports the file and line, and the rest of the file still runs; at startup errors go to stderr, and the first shows in the status line in the warning colour until the next key. Until the full command line exists (milestone 6), files take only the commands that exist so far, `set`, `highlight`, the `map` family and `source`, and the `:` prompt those and a few of its own (see The `:` prompt). User-facing details are in `docs/configuration.md`.
- **Command file syntax (decided in milestone 3).** A command a line; a line starting with `"` is a comment, as in Vim. Arguments are separated by spaces, and as in a shell, double quotes keep spaces in an argument (`set font="C:/My Fonts/Mono.ttf"`), with `\"` and `\\` inside; but a map command's keys are taken as they are, since `"` is a key. `highlight ROLE #rrggbb` sets one role's colour, so the cursor's text is `cursor-text` rather than a foreground half of a `cursor` group: roles are named in lower case with hyphens, one colour each. The map commands are `nmap`, `vmap`, `imap`, `omap` and `cmap`, each `KEYS COMMAND ["HINT"]`, with `nunmap` and so on; there is no plain `map` (Vim's covers three modes, which surprises), and no `noremap`, since bindings name commands rather than other keys. `source FILE` runs a file relative to the one running it.
- **Settings registry and generated config (decided in milestone 3).** Every setting is registered with its name, type, default, range and a one-line description, which later also drive `:set` completion, hint labels and error messages. Setting names are lower case without hyphens, as Vim's options are (`timeoutlen`, `fontsize`), while command names have hyphens (`cursor-left`). The first settings are `theme`, `font`, `fontsize`, `minsize` and `timeoutlen`. `modal --write-config FILE` (with `--force` to overwrite) and, with the `:` prompt, `:write-config FILE` (`:write-config!` to overwrite) write every setting, key binding and colour, in sections, each with a comment saying what it does, and list the commands keys can be bound to. What differs from the defaults is written as commands (settings with their current values, key bindings as `nmap` and `nunmap` lines against the built-in `modalrc`, colours as `highlight` lines against the chosen theme); the rest is commented out at its defaults, so a user changes only what they want and keeps later improvements to the rest, and what they're using now, including a size set with `Ctrl-+`, is kept (decided in milestone 3). Read back, the file gives the same config. A relative FILE is in the config directory for `:write-config` (the program's own current directory means little when started from a menu) and the current directory for `modal --write-config`, which reads `modalrc` first. It writes to a named file rather than to stdout, since its one use is to start a config file, and on Windows `modal` has no console. It is never written automatically.
- **The command registry in use (decided in milestone 4).** The default key bindings stay in the built-in `modalrc`, the only place they're written; the registry looks up a command's current keys from the live keymap when it shows them (the hint menu and the palette), so they show a user's own bindings. For now an entry gives its arguments as a usage string (`FILE`, `NAME=VALUE...`); typed parameters with defaults come in milestone 6, with completion, the palette and the transforms. Every command can be run at the `:` prompt by name or alias, with `!` where it takes one, and a command that takes a count takes it as its argument (`:cursor-down 3`), since `:3` will mean "go to bar 3". Only the config commands (`set`, `highlight`, the `map` family and `source`) can go in a config file; any other command there is an error saying it can't be used in a config file, since the views don't exist yet when the file runs and moving a cursor at startup means nothing. So "anything you can type there can go in the file" now holds for the config commands, and the prompt takes more. The program describes every command before the config is read, since the config binds keys to them; the views and the window attach what runs theirs once they exist, and keys and the `:` line both run commands through the registry. A view that registers its commands can't be copied or moved.
- **The `:` prompt (decided in milestone 3).** `:` opens a prompt in the bottom bar, in command-line mode, whose editing keys are `cmap` bindings in the built-in `modalrc` (Enter, Escape, Backspace, Delete, the arrows, Home, End, `Ctrl-U`, Up and Down); any other character is typed, and Backspace on an empty line closes it, as in Vim *(changed November 2026, after use: it does nothing, in every line typed into, the prompt and its questions, search, the palette, the inspector and the event list's cells, so a press too many when clearing a name can't throw the question away, nor the next go back a view; Escape gives a line up)*. Digits are counts only in Normal, Visual and operator-pending modes, so they're typed at the prompt. Up and Down recall the session's lines; Tab completion waits for the full command line (milestone 6). The prompt runs the command-file commands, `set NAME?` to show settings, `source` with no file to run `modalrc` again (over the current state, as Vim's does), `write-config`, and `q` or `quit`. Settings, bindings and colours apply at once. Errors show in the warning colour and results in the `message` colour.
- **Completion and pick lists wherever there's a fixed set (decided in milestone 4, built in milestone 6 or, where the views need it, sooner).** Wherever a value comes from a known set, Modal offers it rather than making you remember it: command names, settings and their values (a theme, on or off), output ports, tracks, sections, labels, files. At the `:` prompt, Tab completes the command or argument under the cursor, cycling through matches, with the matches shown above the prompt. A command run without an argument it needs (`:port`, `:e` with no file aside, which has the system's dialog) opens a pick list of the choices, palette-style, filtered as you type and chosen with Enter; one whose argument is optional still says what it is when there's no list to pick from. Each command's parameters in the registry name their kind (a port, a track, a setting's value and so on), and each kind has one provider of its choices, so the prompt, the pick list, the palette and the hint menu all offer the same ones. Until then, `:port` alone lists the ports in the status line.
- **Completion at the prompt, as built in milestone 6 (October 2026).** Each command says what kind its arguments are (`choices`: a command, a setting, a theme role, a port, a file from the current directory or from the config directory, a section, a meter, a note length; the third holding for any after it, as `set` takes settings one after another), and each kind has one source of choices: the workspace's own for commands, sections, roles, ports, meters and lengths, the program's for settings (with their values, theme names for `theme`, `on`/`off`, or the value now) and files. Tab works as zsh's does (decided October 2026, rather than Vim's, which jumps to the first match): the first completes the word as far as its matches agree, showing them in a panel above the prompt as the hint menu is shown, none chosen even when it can go no further (so `:` then Tab lists every command and typing narrows them; decided October 2026, after use); after that Tab goes round them and Shift-Tab back, the one chosen in the cursor's colours; a single match is completed with a space after it, unless it goes on (a setting's name, a folder's `/`). A setting completes to its name alone, so `?`, `=` or `!` can follow, and Tab again on a whole name (no other's start) goes on to its values, as `name=` does (changed November 2026, from completing to `name=`, after use). A word matches the choices starting with it, ignoring case, or if none, those with a word starting with it (`del` finds `bar-delete`); fuzzy matching is the palette's. Commands read as actions on what they act on (decided October 2026, after use): `note-default` became `default-note-set`, `section-strip` `go-section-strip` (beside `go-first`), and `:section NAME` `:section-split NAME`, which splits the section at the cursor's bar line rather than making new time; `section-split` sits beside `section-rename`, and `port`, `grid` and `len` stay as they are, setting a value or showing it as Vim's options do. Only commands that do something where the cursor is are offered, nor are the arguments of one that doesn't; while the matches show, Down and Up go round them as Tab and Shift-Tab do, Left and Right go across the columns and Page Down and Up a screen (stopping at the ends), so the line's cursor doesn't move then, and typing or deleting in the word narrows or widens them to what's typed, none chosen, until the word ends or nothing matches; more columns than fit across scroll to keep the one chosen in view, a ◀ or ▶ at the side with more (decided October 2026, after use). A command run where it does nothing says where it's for ("Note default is for the piano roll"), rather than that it isn't in the view, which read as if it were missing. Pick lists for a command run without an argument it needs, and parameters' defaults, come with the palette and the transforms.
- **Prompts on a row of their own (decided November 2026, after use).** Nothing covers the status line, whose transport stays in view. The `:` prompt, search's `/`, a question's answer and the palette's line each go on a row of their own just above it, starting at the left edge, the status line still showing the mode the prompt was opened from. **The palette** follows Doom Emacs's M-x: its line at the top, the matches below it, the best first, or sections, tracks and labels in song order from the top, so Down (and Ctrl-n) goes on to the next and Up (and Ctrl-p) back, and Home and End go to the first and last. It's always as high, `palettelines` matches (10 by default, fewer if the window is small), blank rows below fewer matches, so its line stays put as they narrow; the line shows at its right how many match, or the one chosen among them (`3/12`). **Completion's matches** at the `:` prompt are a small popup instead of a panel of columns, since completion is lighter than the palette: just above the word being completed, starting over its first character, as wide as the longest match, up to ten high and scrolling beyond, with the first match nearest the line. Up goes on through them and Down back, as they look, stopping at the ends: from none chosen, Up takes the one nearest the line and Down the top one shown, where the eye starts (revised after use, when Down from none went back round to the last match, far off, and the list jumped there); Shift-Tab from none also starts at the top one shown, and Tab still goes round. Page Up and Down go a popup's worth, and a ▲ or ▼ shows where there are more. This replaces the columns going across with Left and Right, described above.
- **Long messages (decided October 2026).** A message too long for the status line, with what's beside it, is shown whole, wrapped at its words, in a panel just above the status line in its colour, until the next key, rather than cut off with no way to read the rest on a small screen; the status line shows its start as before.
- **Status bar.** Built from named segments (mode, position, tempo, time signature, key, loop/punch, record state, MIDI activity, pending keys, message), each with a format string, arranged left and right in configuration, like a Vim or Doom Emacs modeline.

## Input and recording

Recorded events are timestamped by the engine at arrival, never by the UI, so recording accuracy is independent of screen activity.

- **Real-time recording:** optional count-in, metronome as MIDI notes to a chosen port, input quantise off by default. Recording goes to the armed track(s); thru to the track's output so you hear the right sound while playing.
- **Loop recording:** each pass is kept as a separate take; version 1 merges or keeps the last, take lanes come later. Looping a section is the usual way in (see Sections: looping, takes and count-in).
- **Punch in/out:** set by labels or the current selection.
- **Step entry from a MIDI keyboard:** play a note or chord; it is entered at the cursor with the default note length (see Editing grammar), and the cursor advances. Keys on the computer keyboard change the length, insert rests and tie.
- **Step entry from the computer keyboard:** in Insert mode, letters enter pitches (e.g. `c d e f g a b` plus accidentals and octave keys) and digits set durations.
- **Playable computer keyboard (later):** a tracker-style key-to-pitch layout using physical scancodes, with proper note-off on key release.
- **MIDI thru and filtering:** per-input filters for channel, message type and range.
- **What is recorded (decided in milestone 2).** All channel messages are recorded and sent thru. SysEx is recorded but not sent thru, since WinMM blocks while sending it; it reaches the engine in fixed-size chunks, so nothing allocates, which limits one SysEx to 32 KB. MIDI clock, active sensing and the other system real-time and system common messages (such as MTC and song position) are ignored.
- **Replace (decided in milestone 2).** On the armed tracks, events starting between the record point and where recording stopped are removed, and an earlier note running into that range is cut short at the record point.
- **Count-in and recording (decided in milestone 2).** Anything played during the count-in is dropped, except what is still held at the record point: a held note starts there, and so does a held pedal. Other controllers moved during the count-in are dropped. Recording carries on past the song's end until stopped, with the metronome still playing.
- **Pedals (decided in milestone 2).** Sustain (CC 64), sostenuto (CC 66) and soft (CC 67) are stored as ordinary CC events, never folded into note lengths. So that a take never leaves a pedal down: a pedal still down when recording stops gets a pedal-up at the stop point, as held notes end there. When replace cuts through older pedal data, the old material is patched at both edges: a pedal-up at the record point if the old track had the pedal down there, and a pedal-down at the stop point if the old track had it down there, so what follows sounds as before.
- **Takes (decided in milestone 2).** A take is collected while recording and applied to the song when recording stops, as one edit, so a recording pass can later be one undo step. Each armed track gets its chosen input (or all inputs), on its own channel. The recorded range runs from the record point up to, not including, the stop point. A note played on a pitch already sounding in the take, from any input or channel, ends the earlier note where the new one starts, and at the same tick replaces it; overdubbing applies the same rule between the take and the old notes (whichever starts first ends where the other starts, and at the same tick the take's note wins), so recording never creates overlapping notes of one pitch. A note whose note-on and note-off arrive on the same tick lasts one tick. Overdubbing doesn't patch pedals at the record point, but if the take lets a pedal up at the stop point where the old track had it down, the old pedal goes down again there.

**Recording in the GUI (agreed design, November 2026)**

- **Which inputs.** *(Superseded 10 November 2026 by the Ports view, below: the enabled inputs are listened to, and the `inputs` and `port` settings are gone.)* An `inputs` setting in `modalrc` named the input ports to listen to, matched as `:port` matches output ports, separated by commas; empty, the default, listened to every input port found. Ports differ between machines, so the choice is the machine's rather than the song's. Modal's own ports are never listened to, so Thru can't feed back into itself. At most 16 are opened, the engine's limit; a name that isn't found is reported in the status line, as missing output ports are. The agreed per-track input extension is described below; schedule.md tracks its implementation.
- **Changing inputs safely (decided 10 November 2026).** Changing the machine's `inputs` setting closes all old input callbacks, then asks the engine to drain their remaining messages and release held Thru notes and pedals. Replacement ports do not open or reuse input IDs until that reset is acknowledged. The GUI polls without waiting on the engine, retrying if its command queue is full, and opens the latest requested set if settings change again meanwhile. Playback continues; this is not a panic or global controller reset. As all inputs are currently reopened together, all held Thru state is released. Queued input remains available to the control side.
- **Arming.** Each track is armed on its own, like mute and solo, so several can be armed and each records the whole take on its own channel. As arming a track while another is still armed is often a mistake, arming one while others are armed says which others are, gently, in the status line, and starting to record onto more than one names them all.
- **Arm and Thru in the Tracks view.** Buttons after Mute and Solo: Arm `R`, Thru `T`. Like the other buttons they have no headings, and show their letter grey when off and filled with their colour when on; Thru on a track not armed shows its letter in its colour, unfilled, since Thru only reaches armed tracks. Arm is bright red, so an armed track stands out, with Mute a lighter pink. The inspector says first what the column under the cursor is, much as a tooltip would, and shows only what concerns that column, as the bar above names the track (revised after use). `, r a` arms or disarms the current track and `, r t` switches its Thru, from any view with a track, and on a Visual selection of Tracks rows every row takes the opposite of the cursor's. Both are undoable edits, saved with the song (`arm`, `thru=off`), and take effect at once, playing or not.
- **Starting to record.** `R` records from the play-from marker, as Space plays from it, with the song's count-in or pre-roll before it; Space stops, as does panic. The `, r` leader group holds the recording commands and settings. (Built 11 November 2026.) With no track armed, `R` is refused, saying `, r a` arms a track; while playing it's refused too, as starting to record partway through is punch-in, which comes later, and `Ctrl-Space` while recording is refused, as playing from elsewhere would end the pass. Recording carries on past the song's end until stopped.
- **The click's port (decided 11 November 2026).** Recording clicks on the song's metronome port (set on the Metronome page), or the default output where it names none, on its channel (10 unless the song says otherwise), with the song's count-in. With neither, it records without a click or count-in, and says so as it starts.
- **The take** goes into the song when recording stops, onto the song as it is then, so edits made while recording stay, as one undo step (`Record onto Bass`, or `Record onto 3 tracks`), the last section growing to the bar line after it where it runs past the song's end. Stopped during the count-in, nothing is recorded and no step is made.
- **The take as it's played (decided 12 November 2026).** While recording, every view shows the song as it would be if recording stopped now: notes as they're played, a held note growing with the playhead, the song growing past its end, and in replace mode what's being replaced going as the playhead passes it. The song itself is changed only when recording stops, so undo, saving and playback are unaffected. Meanwhile an edit, undo or redo that would change the events of a track being recorded is refused, saying it's being recorded; other tracks, and the recorded tracks' settings, can still be changed.
- **What's heard while replacing (decided and built 12 November 2026).** In replace mode, a track being recorded is silent from the record point, as replace will leave it: a note sounding there is cut and a pedal held there let up, and nothing after it plays. Before the record point, through a pre-roll, it plays as usual, and its program and controller values are still set up, so Thru sounds right. A track armed but with an input that can't be used, which records nothing, plays on. In overdub, what's there is heard. No setting, for now.
- **Replace or overdub** is a song setting, saved with the song (`record mode=overdub`, left out for replace), switched with `, r m`, an undo step like arming. The status line shows `● REC` or `● ODUB` while recording, in the warning colour, in place of the transport's symbol so it shows however narrow the window; and while stopped, `Armed 2 Replace` beside the `In` light.

### Per-track input and monitoring

Agreed design, 10 November 2026.

A track's `input` names an input port, as `port` names an output; empty is the machine's default input, set in the Ports view, and `*` every input listened to. It starts empty, shown as **Default**; **All** is every input enabled in the Ports view (a default input decided 11 November 2026, replacing the initial All inputs). It is saved with the song (`input="…"`) and resolved when the plan is built, so Thru and recording take that track's input only from its port. A track naming an input not found is left out of Thru and reported missing. An Input column before Output uses the same chooser, listing input ports, and is in the warning colour with an inspector warning when its port can't be used (see The Tracks choosers, under Ports).

Input activity is an `In` light on the status line's right, lit briefly as input arrives, with the last channel message in, other than a note-off, and its channel, in a fixed width so the status line keeps still (`In  1 C4      96`, `In 10 CC64   127`, `Prog`, `Pres`, `PPrs` for poly pressure, `Bend +8191`; decided 11 November 2026 after the 8.2 trial, as only notes were shown before and their width moved what followed), visible in every view. A machine-level `thru` setting in modalrc, on by default, has `, T t` to switch it; the status line says when it is off. Turning machine-wide Thru off blocks new messages while releases for notes and pedals already held still reach their original destinations; it does not stop playback or input monitoring. The input light remains lit for 150 ms after the last collected message, and the last note-on pitch and velocity remain visible after it fades; note-offs and other messages do not replace that note. The chooser lists active inputs, retaining an unavailable saved name with a warning. Named inputs, and the default, never fall back to All when unavailable. ### Ports

Agreed design, 10 November 2026. Built in steps, November 2026: the `ports` file, resolution and the settings removed; then the view; then its layout after trial, with a default input. It replaces the `inputs` and `port` settings and the placeholder for port aliases, and comes before linear recording.

- **The Ports view** (`, v m` or `gm`, m for MIDI, `, v p` being the piano roll; or `:ports`) lists the MIDI ports Modal has seen on this machine in two groups, **Inputs** and **Outputs**, each headed. MIDI ports are one-way and the system lists inputs and outputs apart, so a device with both, such as an audio interface, appears once in each group, as two ports. Each row shows the port's detected name, with its device or client name where that's needed to tell two ports apart; its **alias**, edited in place; whether it's **enabled**; and whether it's present now. One port of each group is marked as the default, for tracks set to Default (a default input decided 11 November 2026, so both groups work alike).
- **Aliases** are per port, so a device's two sides can be named apart (`Babyface In`, `Babyface Out`). Without an alias, a port is known by its detected name.
- **Enabled ports only are used.** An enabled input is listened to, for Thru, recording and the `In` light; an enabled output is offered to tracks. A disabled port is grey on the page, isn't opened, and isn't offered in the Tracks choosers. A port Modal sees for the first time starts disabled, so dozens of ports needn't crowd the lists, and a virtual port such as loopMIDI is never listened to by surprise (whose input side heard Thru's own output and fed it back, in the 8.2 trial).
- **Ports that come and go.** The list follows devices being plugged in and out where the system reports it (on Windows by looking ten times a second, on Linux as ALSA announces it), looks again whenever the view is opened, and `:ports-refresh` looks at any time. A port that isn't present stays listed, dim and marked absent, keeping its alias and whether it's enabled, until a command forgets it.
- **Stored per machine,** in a `ports` file in the state directory beside `remembered`: plain text, written by Modal whenever the page changes, never by editing `modalrc`, which stays the user's own (as Vim keeps `vimrc` and `viminfo` apart). Ports belong to the machine, not to the user's settings or the song.
- **Songs save aliases.** A track's output and input name the alias, so a song plays on another machine whose ports are given the same aliases. A name resolves to an alias first, then a detected name, so songs saved before this keep working. A track naming a port that's missing or disabled shows it in the warning colour, and the inspector says which and, for a disabled one, to enable it in the Ports view; it never plays to, or listens to, another port instead.
- **The Tracks choosers** list the enabled ports by alias, after **Default**, and for inputs **All** (every enabled input). In the cells, `Default` and `All` are dim, as following the default rather than set on the track; a missing or disabled port is in the warning colour; others are ordinary text. `Default` with no default set, or with a default that's missing or disabled, is in the warning colour too, as the track plays or hears nothing, and so is `All` with no input enabled, or none of those enabled connected (decided 11 November 2026); a machine with no MIDI ports at all shows every track so. The inspector on the cell says which, and where it's put right. The headings are **Input** and **Output**, in that order, with three blank cells between them (built 11 November 2026, Input first after trial, as MIDI flows: Input beside Arm and Thru, Output beside the channel, bank and program it plays with). The bar above names the track's output as `Output:`.
- **In the view (built November 2026, laid out after trial).** Each group has its heading, a blank line, then its own column headings, **On**, **Default**, **Alias** and **Port**, over its ports; two blank lines part the groups. `j` / `k` go from port to port, past the headings, and `h` / `l` along the columns: **On**, a green `✓` when enabled and a grey `✗` when not; **Default**, a radio button, `•` for its group's default and `◦` for the others, one at a time; **Alias**, a field; **Port** (the detected name), the cursor going no further; and after it, read only, `not connected` if it isn't (the cursor stopped at Port after trial, 11 November 2026, as on a connected port it had only a blank to land on). Enter or `e` on On or Default switches it; on the alias it edits the alias in place, Enter setting it and nothing clearing it. The detected name is read only, Enter doing nothing on it (decided after trial, 11 November 2026: the alias's editor, opened from the name, was out of sight in the Alias column, the cursor held until Enter or Escape). An alias is unique among its direction's ports, aliases and unaliased names alike, as tracks name a port by it, and can't be `Default`, `All` or `*`, the choosers' own. A disabled port's row is grey; one enabled but not connected says so in the warning colour. `x` forgets a port that isn't connected; one that is would only be found again, so it's refused with a word to disable it instead. The inspector says what the column under the cursor is, then why the port can't be used if it can't, then its detected name whole. The bar counts the enabled ports of each kind. Changes are the machine's, kept at once in the `ports` file, and not undo steps.
- **Starting clean.** The `inputs` and `port` settings are removed, with no migration (decided 10 November 2026, Modal having no other users yet). Without a `ports` file every port starts disabled, so nothing plays or listens until ports are enabled in the Ports view, and the status line says so while none is.

**Sections: looping, takes and count-in (decided October 2026)**

- **Looping:** `, L` loops the section the cursor is in; a run of sections selected on the strip loops as a range.
- **Passes:** loop recording over a section handles each pass by a setting: **takes**, each pass kept as a separate take of the section on the armed track, or **overdub**, each pass merged into one layer (MPC-style), building a part up pass by pass. While overdubbing, holding an erase key (to decide) and pressing notes on the MIDI keyboard removes those pitches as the playhead passes.
- **Takes** are stored with the section, per track, so they move with it. `]t` / `[t` go through the current section and track's takes, auditioning each; one take is the active one, and a command makes the current take active and can discard the others. Comping (combining the best parts of several takes) comes later.
- **Count-in for takes,** a setting: the first pass only, then seamless looping; every pass, with a count-in (metronome only, the music silent) between passes to give time to reset; or a pre-roll before each pass, playing the last few bars of the previous section so the player comes in with the song's context. Count-ins use the conductor's meter. Each pass, with its count-in or pre-roll, is one undo step.

## Playback and recording behaviour

- **Chasing.** When playback starts mid-song, each track first sends its latest program change, CC values, pitch bend and channel pressure from before the start point, then note-ons for notes already sounding, for their remaining duration. A track that becomes audible during playback, by being unmuted, by a solo being released or by being rerouted, catches up the same way, as it would otherwise carry on with the wrong sound or controller values (decided November 2026): its setup, then its values, whatever its chase setting, then if it chases notes those still sounding. Note chasing can be turned off per track, for drums and other sounds where a late attack sounds wrong. Chasing is per track (two tracks on one channel each send their own values), the values go out in the order they were originally sent (so bank select stays before program change, and RPN/NRPN sequences stay in order), and "before the start point" means stored position, not offset send time. Not chased: channel mode messages (CC 120–127), poly aftertouch and SysEx.
- **Mute and solo.** If any track is soloed, only soloed tracks play, even a muted one; otherwise unmuted tracks play.
- **Playback transpose and velocity offset.** A note transposed outside 0–127 isn't sent, and the player reports how many notes each track loses this way. Velocities are clamped to 1–127 after the offset, never 0 (which would be a note-off).
- **Tempo.** The tempo map is evaluated at the start position, so playback begins at the right tempo. Tempo is internal timing, not something sent as MIDI.
- **Track time offset.** As in SPG, each track has a time offset in milliseconds (−1000 to +1000), a track setting like transpose, applied at playback only. It shifts every event on the track, e.g. sending slow-attack string chords 40 ms ahead of the beat. Milliseconds rather than ticks, since it usually compensates for a real-world duration and should stay the same at any tempo. Stored events never move: the event list shows their positions as entered, and the offset is shown with the track's other settings (track header, inspector), never hidden. For a negative offset at the playback start point, the engine starts its clock early by the largest negative offset of any track, so early events still play in time. The metronome and MIDI clock are never offset. Recording onto a track with an offset subtracts it, so takes play back as they were heard.
- **Overlapping notes.** When notes of the same pitch on the same channel overlap, each new note retriggers (note-off, then note-on), and the final note-off is sent at the latest end of the overlapping notes, so a long note keeps sounding past a short one inside it. The editor never creates overlapping notes; overlaps in imported files are kept as they are, since the data is shown honestly.
- **Stop.** Note-offs are sent for every note currently sounding. The scheduler remembers which channels it has left with a pedal down (sustain, sostenuto or soft) and sends a pedal-up to just those, always (decided in milestone 2), up to 256 pedals; it does the same when playback restarts from another point while playing, before chasing there. All Notes Off and a sustain reset on every channel used are optional, off by default. A panic key stops playback and sends All Notes Off and resets controllers on every channel of every port playback has used.
- **Transport (GUI).** Easy ways both to stop and resume from where playback stopped, and to stop and replay from where it last started. The interim `modal-play` has only stop and resume (space).
- **Tracks and channels.** As in SPG, each track has exactly one output port and one MIDI channel. Notes recorded on any input channel are rechannelised to the armed track's channel. Multi-channel tracks in imported MIDI files are split into one track per channel.
- **Recording.** Recording replaces existing material in the recorded range by default; overdub (merge) is a setting.
- **Cueing: queued section jumps (decided October 2026).** During playback a jump to another section can be queued, to happen at a musical boundary. Move the cursor to any section (which doesn't interrupt playback) and `Shift-Enter` cues a jump to it, or `:cue Chorus` by name. Cue slots give instant cues: `F1` to `F12` by default (to decide), reassigned for the session with `:cue F3 Bridge` or saved with the song. Cues are ordinary commands, so they can go in macros or on keys, such as a key that cues Verse 2 then Chorus; a fuller playlist of sections, like an MPC's song mode, could grow from this. The jump happens at the end of the current bar or of the current section (a setting, to decide; `:cue Chorus now` overrides it). If looping, the loop moves to the new section. The status line shows the cue, and cueing it again, or `:cue cancel`, cancels it.
- **MIDI clock (proposal).** A keyboard-driven transport and sync settings screen chooses which ports send MIDI clock, Start/Stop/Continue and Song Position Pointer. These settings are stored in the song, with port names resolved through each machine's port aliases.

* **Panic.** `Ctrl-.` (a full stop, literally) stops playback and sends All Notes Off and resets controllers on every channel of every port playback has used, in every mode. The interim command-line tools use `!` while playing and a `--panic` option instead, since terminals can't reliably detect `Ctrl-.`.
* **Recording input.** Armed tracks listen to all MIDI inputs by default; each track can optionally be set to one input.
* **MIDI thru.** On by default, so you hear the armed track's sound while playing; can be switched off globally or per track.
* **How thru behaves (decided in milestone 2).** Thru works whether or not the song is playing, so sounds can be tried before recording. It goes to every armed track with thru on, including muted and un-soloed ones, since thru is how a track being recorded is heard. Each gets the track's channel, transpose and velocity offset (so you hear what playback will sound like) but not its time offset. The engine remembers where each held thru note and pedal went (up to 1,024 notes and 256 pedals; a note-on beyond that isn't sent), so its note-off or pedal-up goes to the same place even if the track is disarmed or changed meanwhile. Stop leaves held thru notes alone, since their note-offs will follow; panic ends them, and reaches thru's ports too. Thru delay, from arrival to just after the send call, is measured separately from playback lateness.

## Metronome and count-in

The metronome is part of milestone 2, since recording depends on it.

- **Sound.** Sent as MIDI notes to a chosen port and channel (e.g. a drum module, or a plugin via Carla), with separate notes and velocities for the downbeat and other beats. Once in-process audio exists, a built-in click becomes an option.
- **When it plays.** Off, during recording only (default), or always.
- **Which meter it follows.** The conductor's meter by default; optionally the cursor's track, for practising a part in a different meter.
- **Count-in.** None, 1 bar (default), 2 bars, or a custom number of beats, in the meter at the record start point.
- **Pre-roll.** As an alternative to a count-in, playback starts a set number of bars before the record point, so you play along with the song before recording begins; useful with punch in.
- **Subdivision.** Optional clicks on eighths or sixteenths for slow tempos.
- **Defaults and generation (decided in milestone 2).** Channel 10; downbeat note 76 (Hi Wood Block) at velocity 110, other beats note 77 (Low Wood Block) at velocity 80, each a 1/32 note long. The port is chosen when recording until GUI metronome controls exist (see schedule.md). The scheduler generates the clicks from the reference meter and tempo map rather than the plan's events, so they carry on past the song's end; they are never offset, muted or soloed. Count-in uses the tempo and reference meter at the record point.
- **Clicks (decided in milestone 2).** One click per beat, the beat being the time signature's denominator (so 6/8 clicks six eighths), with the first beat of each bar accented; other divisions, such as dotted quarters in 6/8 or the subdivisions above, come later. Playback starting mid-beat first clicks on the next beat. A click is cut short where the next beat comes sooner than its length. When recording, the metronome carries on past the song's end until stopped; in plain playback with the metronome always on, it stops when the song ends (with the last note-off), since there it is a timing reference for the song rather than a practice click. Whether this playback records (for "during recording only") is decided on the control side when the plan is compiled, so the engine needs no recording flag.
- **Count-in and pre-roll (decided in milestone 2).** One song setting chooses none, a count-in (1 bar by default, or a custom number of beats) or a pre-roll (1 bar by default). A count-in always clicks, whatever the metronome's "when" setting, since otherwise there's nothing to count with; without a metronome port there is no count-in. It comes before the record point with the song silent, at the tempo there, and runs the record point's meter backwards, so its accents fall where bars would start: from beat 3 of 4/4, a 1-bar count-in clicks beats 3, 4, 1 (accented) and 2. It is planned on the control side and carried with the play request, like chased events, so the engine allocates nothing; its clicks are at fixed times, so a tempo edit during a count-in doesn't move them. If a track's negative time offset reaches further back than the count-in, playback starts that much earlier. A pre-roll goes back the length of the bars before the record point's bar, keeping the position in the bar, and starts at bar 1 if there aren't enough bars.
- **Quick toggles.** On the `, m` leader menu (metronome on/off, count-in length, pre-roll), and as status-line segments. As built (11 November 2026): `, m m` cycles the metronome off, while recording and always, and `, m c` what comes before recording, nothing, a count-in or a pre-roll; `:countin 2`, `:countin 3 beats`, `:countin off`, `:preroll 2` and `:preroll 3 beats` set the lengths, and alone say what's set. Each is a song setting and an undo step.
- **The Metronome page (decided and built 11 November 2026).** `, m s` or `:metronome` shows every setting, so none is hidden behind a command's arguments: under **Metronome**, Plays, Port, Channel, Downbeat and Beat (each a note, its General MIDI drum name, and a velocity) and Length; under **Before recording**, what comes before (nothing, a count-in or a pre-roll), and the count-in's and pre-roll's lengths, each a number and then Bars or Beats (pre-roll in beats added after trial, 11 November 2026, for symmetry). `j` / `k` move between rows and `h` / `l` between a row's fields: a click's note, velocity and **Test** button, which plays it. Enter edits a typed value in place (a note by name or number, a length as 1/32), Up and Down stepping it (a note by a semitone); a digit on a number field starts typing it without Enter (a note by number), digits elsewhere being a count. Plays, Before, Port and Bars/Beats are chosen from drop-down lists (see Drop-down lists). Changing a click's note or velocity plays it once, through the engine on the click's port. Typed fields have a cell for the cursor beyond their longest value, so a velocity's three digits show as they're typed. The inspector says what each row is for, and on Port, in the warning colour, when there's nowhere for the click to go. The page is the place for the song's MIDI clock and sync settings when they come.
- **Drop-down lists (decided 11 November 2026, after trial).** A field with a fixed set of choices opens a list of them under it with Enter, rather than Enter then Up and Down going through values unseen: Up and Down (or `j` / `k`) move through it, Enter (and in the inspector Tab) takes the one highlighted, Escape leaves the field as it was. Each such field shows `▾` at its right, on a field's background as a typed field is, so the value and its arrow read as one control (added after trial, 11 November 2026). Long lists of names, the ports, narrow to what's typed; short ones have nothing to type, a letter going to the next choice starting with it. They're the track's Input and Output, playback quantise's Moves, and on the Metronome page Plays, Port, Before and Bars/Beats. Note lengths (quantise's Grid, the click's Length) stay typed with Up and Down, having a dozen or more values quicker typed; controllers stay typed by number or name; on/off buttons stay toggles.
- **In the status line (decided 11 November 2026).** While recording, `● COUNT` through a count-in and `● PRE` through a pre-roll, then `● REC` or `● ODUB`, all one width so the transport doesn't move. Stopped with tracks armed, what comes before recording beside them (`Armed 1 Replace  Count-in 1 bar`), the first thing left out where the line's too full; and `No click` in the warning colour when the click has nowhere to go, as a message at the start of recording was easily missed. With the metronome always on, a dim `Click` while playing.

## File formats

Songs are saved in a plain-text format designed to be read, diffed and version-controlled with git. Standard MIDI Files are the interchange format with everything else.

**Native song format (sketch; details settled in milestone 4)**

```
modal-song 1
song "Untitled" ppqn=960
track 1 "Bass"  ch=1  port="Pro-800"
track 2 "Drums" ch=10

section "Intro" bars=4
  tempo 1:1:0 120
  meter 1:1:0 4/4
  label 3:1:0 "fix this fill"
  track 1
    1:1:0  note E1  v=96  len=1/8
    1:3:0  note E1  v=88  len=1/8.
  track 2
    meter 1:1:0 7/8
    1:1:0  note C1  v=110  len=1/16

section "Verse 1" bars=16 colour=blue
  …
```

- One event per line, positions as bar:beat:tick so diffs are readable. Absolute positions within a section mean inserting an event changes only one line, and positions relative to the section mean moving or duplicating a section changes nothing inside it.
- Ports are stored by name, with a mapping file per machine, so songs move between computers.
- **Format (decided for milestone 4, and for sections in October 2026).** The first line is `modal-song 1`, the format's version. Then `song "Title" ppqn=960`, then the tracks, each a `track` line with its settings (`ch=1 port="…"`, `transpose=+2`, `mute`, `grid=1/16`, `len=grid` and so on). Then the sections in order, each a `section "Name"` line with its length as `bars=N` in the conductor's bars and its settings (`colour=…`), followed by the conductor's `tempo` and `meter` lines and the section's `marker` lines, positioned in the conductor's bars, and then each track's content in the section: its own `meter` lines, if it has its own meter there (a track with none follows the conductor; there is no shorthand for a meter matching the conductor's, so changing the conductor never changes how other tracks are written), then its events, positioned in its own bars. Positions are relative to the section: its first bar is bar 1. A track with nothing in a section is left out of it. How a section refers to a track is settled with the format's details. Note lengths are note fractions where exact (`len=1/8.`), else ticks (`len=437`), since a length in bars depends on the meter. Tempo is in BPM with as many decimals as it takes to read back to the exact stored microseconds per quarter note. SysEx is hex bytes (`sysex F0 43 … F7`). Text is in double quotes with `\"` and `\\`, and `\xNN` for bytes that aren't UTF-8, as an imported file's raw text may have. A line starting with `"` is a comment, as in `modalrc`. Files end in `.modal`.
- **Song file details (decided in milestone 4).** After `song`, a `metronome` line (`when=off|recording|always ch=10 downbeat=E5 downbeatvel=110 beat=F5 beatvel=80 len=1/32`, and `port="…"` if set) and a `countin` line (`mode=none|countin|preroll bars=1 beats=0 preroll=1`) give the song's settings in full. Each track line is `track ID "Name" ch=N`, then only what differs from a new track's settings: `port="…"`, `input="…"`, `mute`, `solo`, `arm`, `thru=off`, `chase=off`, `bankmsb=0`, `banklsb=32`, `program=12`, `quantize=on`, `qgrid=1/16`, `qstrength=80`, `qswing=60`, `qmove=both`, `transpose=-12`, `velocity=+10`, `offset=-40ms` or `offset=+218t` (musical offsets rescale with PPQN), and the piano roll's grid and default note, `grid=1/8t`, `len=1/4` and `vel=90` (milestone 5; a default length taken from a note of no common length is a fraction such as `len=437/3840`). The ID is the track's stable ID, saved as it is, gaps and all, and the lines' order is the display order, so moving a track changes only line order. In a section, its `meter` lines come first (always at least one, at `1:1:0`, with any remainder bar written as a change), then `tempo` (always one at `1:1:0`) and `marker`; then a block for each track with anything there, in display order: `track ID`, its own `meter` lines if it has its own meter, then its events. Events are `POS note PITCH v=V len=L` (with `rel=R` when the release velocity isn't 64), `cc C V`, `program P`, `bend V` (-8192 to 8191), `pressure V`, `polypressure PITCH V`, `sysex F0 … F7`, and `text`, `copyright`, `instrument`, `lyric` and `cue` with quoted text. Pitches are named with middle C as C4, with sharps written and flats read. A note length is a note fraction when its denominator divides 768 (down to 1/256 notes and their triplets), otherwise ticks. Positions are `bar:beat:tick` from the section's start, in the bars of the track's own meter or the conductor's. Indentation is only for reading. Anything wrong stops the file being read, with the line given (`song.modal, line 12: unknown event type "notee"`), rather than skipping what can't be read, since a song file is Modal's own data and nothing should be lost without a word. A file at another resolution is read at its own and then rescaled: bar lines land exactly, and positions and note ends round to the nearest tick, separately, so notes that touched still touch.
- **A port that isn't there (decided for milestone 4).** A track keeps its port's name whether or not the port is found. On loading, a track whose port isn't found plays to nothing, the status line says which ports are missing, and `:port` reassigns it; Modal never re-routes a track to another port by itself. Port aliases (see schedule.md) then map a name to a different port on each machine.
- Saves are atomic (write a temporary file, then rename), with optional numbered backups.

**Other files**

- **SMF import/export:** type 0 and 1, preserving tempo map, markers and track names.
- **SMF and sections (decided October 2026).** Export writes the conductor's tempo and meter, and each section's start as a marker meta event, so other software sees the structure. Import makes one section ("Section 1") holding everything, with the file's tempo and time signatures going to the conductor and every track following it, and its markers as labels; turning those markers into sections is an option.
- **Markers and cue points (decided in milestone 4).** Export writes bookmarks as cue point meta events, so they can be told apart from section starts, and writes no section markers for a song of one section, since there's no structure to show (so an imported file exported again gains nothing). Import makes markers bookmarks, and cue points too when they're in a conductor track (one with no channel events, which then needn't become a track); a cue point among a track's own events stays one of its text events, as before. The section is the fewest whole bars that hold everything, including the last note's end.
- **SMF export (decided in milestone 2).** Type 1 by default, type 0 as an option, at the song's PPQN. The first track holds the title, tempo map, the reference meter (now the conductor's) and the markers; then one track per Modal track, with its name and channel. Events are written as stored: transpose, velocity offset, time offset and mute/solo aren't applied, so the file matches the event list. The exception is a track's bank and program setup, written at tick 0 ahead of its events, as other programs would otherwise play the wrong sound (decided November 2026); it reads back as ordinary events, since a file can't mark them as a setup. Port names aren't written until port aliases exist.
- **SMF export details (decided in milestone 2).** Each Modal track gets a channel prefix as well as its name; a type 0 file has only the title as its track name. At each tick come note-offs, then other events in stored order (so a program change precedes the notes it applies to), then note-ons, then the note-offs of zero-length notes, so a note ending and another starting on the same pitch and tick don't cut each other off. Running status is used, and reset after meta and SysEx events. Each track ends at its last event or note end, and the first track at the latest of all, since some programs take the song's length from it. Overlapping notes of one pitch are written as stored; reading them back pairs note-offs first on, first off, which sounds the same in Modal's playback. Tempos slower than an SMF holds (about 3.58 BPM) are clamped with a warning; a resolution above 32,767 or a gap between events over 2^28 ticks can't be written. Files are written to a temporary file and renamed into place. Empty tracks are written, but Modal's own import skips tracks with no events.
- **SMF import rules (milestone 1).** Files are rescaled to the song's PPQN, rounding each note's start and end separately so touching notes still touch. Note-ons and note-offs pair first on, first off; notes still sounding at the end of a track end there. Each file track becomes one track per channel it uses, named "Name (ch N)" when split; its SysEx and text go to the first of those, or to a track of their own if it has no channel events. A track with only tempo, meter, markers and a name (a conductor track) doesn't become a track; in a type 0 file, or a type 1 file whose first track is a conductor track, the first track's name is the song title. Tempo, time signatures (applied to every track) and markers are read from any track. Running status is accepted across meta and SysEx events, split SysEx packets are joined, and escapes other than complete SysEx messages are dropped. Not supported: type 2 files and SMPTE-timed files. Ignored: port and channel prefixes, SMPTE offset, key signature, sequencer-specific events. Text is kept as the file's raw bytes. Damaged files are read as far as possible, and every problem worked around is reported as a warning.
- **Configuration and keymaps:** plain text, in the style of `.vimrc` / `.muttrc`, reloadable without restarting.
- **File commands (decided for milestone 4).** `:e FILE` opens a song, or imports a `.mid` file; `:w` saves, and `:w FILE` saves as; `:export FILE.mid` writes a Standard MIDI File; `:new` starts a new song; `:q` refuses while there are unsaved changes, `:q!` quits anyway and `:wq` saves and quits; `modal FILE` opens a song from the command line. `:e` with no file, and `:w` on a song never saved, show the system's open and save dialogs, through SDL3 (native on Windows, the desktop portal or `zenity` on Linux), much as GUI Vim does.
- **Unsaved changes and overwriting (decided in milestone 4, as Vim does).** `:e` and `:new` refuse while there are unsaved changes ("Unsaved changes: :w saves them, or :e! discards them"), and `:e!` and `:new!` go ahead anyway. `:w FILE` and `:export FILE` refuse to write over a file that exists, other than the song's own, unless given `!` (`:w! FILE`); the system's save dialog asks about overwriting itself. Closing the window (its close button or Alt-F4) with unsaved changes asks, in a system dialog, Save, Don't save or Cancel; without changes it just closes. A new song, or one just opened, is unmodified, so leaving it asks nothing. The window's title names the song as the status line does: `song.modal [+] – Modal`, `song.mid (imported) – Modal` or `Untitled – Modal`.
- **A new song (decided in milestone 4).** `modal` with no file, and `:new`, start an empty song: one empty track, `Track 1` on channel 1, the conductor at 120 BPM in 4/4, and one section of 8 bars, as the core makes a song. `modal --demo` opens the made-up demo song instead, for trying things out.
- **File commands, as built in milestone 4.** `edit` (`e`), `write` (`w`), `export`, `new`, `quit` (`q`) and `wq` are registry commands, run at the prompt; `quit` moved there from the prompt's own commands, so it can check for unsaved changes. A FILE is the rest of the line, quotes around it dropped, relative to the current directory, and given `.modal` (or `.mid` for `export`) if it has no extension. `:w FILE` makes FILE the song's file, as saving as does. The file dialogs offer songs and MIDI files to open, songs or MIDI files to save, and start beside the song's file (or the file it was imported from); SDL answers them on another thread, so the answer comes back to the window's event loop as an event. Saving from the closing question goes through `:wq`, so the window closes once the song is saved, after the save dialog if it needs one. Opening a song looks its ports up again, naming any not found.
- **Port aliases:** per machine, set in the Ports view (see Ports, under Input and recording).

## Architecture

The engine is a separate library running its own high-priority thread; the UI is a client of it. The two communicate only through lock-free queues and atomically swapped song snapshots, so a slow redraw or file save can never delay a MIDI event.

&#91;embedded content: architecture · UI thread, engine thread, MIDI layer\]

The editor publishes a new immutable song snapshot after each edit; the scheduler picks it up between events. Recorded notes and the play position flow back through a queue.

- **Snapshot handoff.** Songs share unchanged tracks through `shared_ptr<const Track>`. Snapshots reach the engine through a lock-free single-producer, single-consumer queue, not `std::atomic<shared_ptr>` (which takes a lock on common standard libraries). Retired snapshots are handed back and freed off the engine thread, so the engine never runs a destructor or frees memory.
- **Playback plan.** Each snapshot is compiled off the engine thread into a flat, time-sorted plan with destination, channel, transpose, velocity offset and mute/solo already applied. Notes keep their durations in the plan; the engine generates note-offs from its own table of sounding notes, which also serves stop, panic, overlapping notes and plan swaps during playback.
- **Engine wake-ups.** The engine sleeps until its next event, or at most 1 ms, so transport commands are seen within 1 ms (within the spin margin just before an event; see Clock).
- **Scheduler.** The scheduler plays a plan without doing any timing itself: the engine passes it the time on each wake-up, so tests drive it with made-up times. At equal times, note-offs go before other events, so touching notes of the same pitch retrigger cleanly. Its table of sounding notes holds 4,096 notes, allocated up front; if it is ever full, a new note-on isn't sent (and is counted), rather than risk a stuck note. Panic reaches up to 64 destinations: every one any plan has used.
- **Plan swaps during playback.** Everything due under the old plan is sent first; playback then carries on from the same tick in the new plan, so a tempo change keeps the bar and beat. Events not yet sent come from the new plan. Sounding notes end at their original tick, at the new tempo and time offset, even if the edit changed or removed the note; notes on tracks no longer in the plan (muted, removed or unrouted) end at once.
- **Stop options.** All Notes Off and sustain reset on stop are scheduler settings, set by `modal-play` flags, until settings exist (see schedule.md). Each is sent once per destination and channel the plan's tracks use.
- **Engine commands.** Play, stop and panic go to the engine through one ordered command queue, so a quick play then stop can't be reordered. The chased events for a play are computed on the control side and travel with the plan snapshot, so the engine never allocates them. The engine keeps the snapshot it replaced alive until its next update, so it can finish with the old plan while switching. When the song ends, the engine reports it and stays in play until told to stop; what happens then is up to the client (`modal-play` exits). The engine reports the tick at which each play stopped (decided in milestone 2), so a take ends exactly where the stop took effect rather than where the control side thought it was. On each pass the engine takes in input before carrying out commands, since that input arrived before the commands take effect: a note that arrives just before a stop is carried out belongs to the take, even if the stop was given first.
- **Input and thru (decided in milestone 2).** Each input port feeds the engine through its own fixed-size lock-free queue of messages timestamped on arrival. The engine wakes as soon as input arrives (the clock has a wake call: an event waited on alongside the timer on Windows, an eventfd polled alongside an absolute timerfd on Linux), sends it thru to the armed tracks' ports and channels, and stamps it with its song tick and its time into the song (so the recorder can take a track's time offset off exactly), since only the engine knows the current time-to-tick mapping exactly, including tempo edits during a take. Stamped input goes back to the control side through a queue (4,096 chunks; what doesn't fit is counted), where the recorder turns it into events. All input goes back, playing or not, marked with the play it arrived during; the control side decides what a take keeps, so a note pressed just before playback and still held at the record point is known about. Input before the song's start (a count-in or lead-in from bar 1) is stamped with ticks before 0, at the starting tempo, so the recorder can tell it from input on the downbeat; the displayed position still stops at 0.
- **Send lateness.** Measured from each message's due time to just after it was handed to the MIDI layer: the engine's wake-up accuracy plus the driver call. This is the figure behind the ~1 ms rule for switching to OS-timestamped delivery; the time a message leaves the cable is what the loopback test measures. It is also reported in its two parts, wake lateness (from the due time to the start of the send call) and send time (in the call), so a slow timer and a slow driver can be told apart. Each is a count, the maximum and a histogram in 50 µs steps up to 20 ms.

- **Engine library (`core`):** song model, scheduler, recorder, SMF and native file I/O. No UI dependencies; usable from a command-line player and from tests.
- **Platform layer:** MIDI outputs behind the scheduler's small message-sink interface, timestamped MIDI input and port lookup by name, all over libremidi; plus thread-priority, clock, console-key and config-directory helpers per OS.
- **Input session.** `MidiInputSession` in the platform library owns the live input ports, their name-to-InputId mapping and asynchronous replacement/reset. The GUI supplies the wanted names and its current millisecond time, polls the returned deadline, and reports errors; the session knows nothing about SDL or UI settings. Ports are destroyed before a reset request, and new IDs are not exposed until the engine acknowledges old-state release. A port's destructor must finish its callbacks. Injected enumeration/opening functions allow lifecycle and callback tests with fake ports; the normal backend wraps `MidiInput`.
- **Bounded input service (decided 10 November 2026).** Each engine pass captures the number of chunks already queued on each input. Ordinary service takes at most 32 whole messages, yielding to another port after eight. SysEx stays whole, so its chunks keep one recording stamp and framing; its size is already bounded by the input queue. Before a transport command, the engine finishes the captured backlog under the old play/mapping, preserving recording attribution. That drain is bounded by the captured queue capacities; later arrivals cannot prolong it. An input reset additionally captures final callbacks after the producers close. The GUI checks an accepted-versus-processed message counter before collecting stamped input and keeps its settle timer running while input is pending, including while stopped. The counters publish completion after stamped chunks, so the final batch is not missed when the timer returns to idle. These are work limits, not measured latency guarantees.


- **Grid UI:** a cell-grid abstraction (characters, colours, attributes) plus optional pixel regions for the piano roll, velocity lanes and arrangement timelines. Rendered with SDL3 now; a terminal backend stays possible later.
- **Rendering (decided in milestone 3).** SDL3's 2D renderer, with text through SDL_ttf (FreeType, without HarfBuzz, since a fixed grid needs no shaping). Each glyph is rendered once into a texture atlas and each cell is drawn from it. Box drawing lines (light and heavy) and block elements are drawn as exact rectangles rather than from the font, as terminals do, since the font's own glyphs leave seams between cells and its partial blocks aren't exact eighths; the shades are flat tints rather than dither patterns, for density shading. Pixel regions are rectangles of whole cells, so they fit the layout, inside which a view draws filled rectangles and lines at exact pixel positions, clipped to the region, in the same pass as the text. The window redraws only when something changes, synced to the display: every frame while the playhead moves, otherwise only on input or a resize, so an idle window takes no CPU.
- **Cell size and high DPI (decided in milestone 3).** The font size is in points, scaled by the display's pixel density. Cells are a whole number of pixels, from the font's advance and line height, so the grid never blurs or drifts. Moving to a display with another scale, or `Ctrl-+` / `Ctrl--`, renders the atlas again. On Windows, SDL3 works in real pixels and reports the display's scaling (such as 150%) as the display scale, so the font is scaled by that and the text is crisp. The window opens at a size in cells (120 × 36 by default), so it's the same size relative to its text on any display.
- **Text size keys (decided in milestone 3).** `Ctrl-+` and `Ctrl--` (`font-bigger`, `font-smaller`) change the text a point at a time, with counts, within `fontsize`'s range of 4 to 72, and `Ctrl-0` (`font-reset`) goes back to the size the config sets; plus is bound as `<C-=>`, `<C-S-=>` and `<C-+>` for the layouts that type it differently, and the keypad's as `<C-kPlus>`, `<C-kMinus>` and `<C-k0>`. The window keeps its size and the grid gains or loses cells, as in a terminal; it grows only to stay at the minimum size. The `fontsize` setting follows the change for the session, but nothing is written to the user's files. The new size and cell size show in the status line in the `message` colour until the next key. These are the window's commands, run by the program around the view, which hands it commands it doesn't have. Thin lines and the space beside them are a hairline, a seventh of a cell's width and at least a pixel, so drawing keeps its proportions at any size.
- **Keys with Ctrl or Alt (decided in milestone 3).** SDL's key code has Shift applied, so the key's own character comes from its scancode in the keyboard layout, unshifted: Ctrl-Shift-d is `<C-S-d>`. The keypad types its characters, so a binding of `+` works from either plus key, except with Ctrl or Alt, when nothing is typed and its keys arrive as `<kPlus>`, `<kMinus>` and `<k0>` to `<k9>`, Vim's names for them.
- **Keys (decided in milestone 3).** Printable keys are bound by the character they type, so `|`, `"` or `D` work whichever key types them on any layout. Ctrl and Alt combinations and special keys are bound by key code, written in Vim notation (`<C-a>`, `<Esc>`, `<S-Tab>`, `<F5>`). Physical scancodes are kept for the later playable computer keyboard. The main modifier is abstract, so it can be Cmd on a Mac. As in Vim, a key that only starts longer bindings waits for the next key, and one that is both a binding and the start of a longer one waits up to `timeoutlen` (half a second by default, a setting) before running the shorter; pending keys show in the status line, with the count. A key that continues no binding runs the keys before it if they're a binding, and is then taken afresh; otherwise it, those keys and the count are given up together, as Vim gives them up, rather than the last key being taken alone (revised October 2026, when `dat`, with no `at`, ran as `dt`), and Escape gives up whatever is waiting. Keys bound to nothing say so on the status line ("Q isn't a key here"; after an operator, "at isn't a range or object after d"), rather than nothing happening (decided October 2026; a setting could quieten it later). After an operator only its own key again takes the cursor's bar (`dd`, `>>`); another operator's key is refused in the same way. With Ctrl or Alt a letter is the same in either case, so `<C-d>` and `<C-D>` are both Ctrl-d as in Vim, and Ctrl-Shift-d is written `<C-S-d>`. A typed character comes from the system's text input, which follows the keyboard layout and dead keys; with Ctrl or Alt, which type no text, it is the key's own unshifted character, with Shift as a modifier. Ctrl and Alt held together are taken as AltGr, which types text on many layouts, so they can't be bound together with a character.
- **UI code layout (decided in milestone 3).** `src/ui` holds the cell grid, layout, key handling, keymaps and the config parser, with no SDL, so all of it is unit-tested directly; `src/ui/sdl` holds the renderer and key translation, smoke-tested through SDL's offscreen video driver in CI; `apps/modal` is the program. `src/ui` links the core library, for ticks, meters and the song model.
- **Test view (decided in milestone 3; replaced by the event list in milestone 4, the arrange page's code and tests staying for milestone 5).** Three pages, gone through with Tab. The grid page has a 1000 × 1000 grid of cells labelled with their row and column, ten characters wide, under fixed column numbers and beside fixed row numbers, as the event list will have fixed headers; above it, a pixel region shows four bars of 4/4 over bars of 7/8 on the same time scale, with bar numbers placed to the pixel and notes. The arrange page sketches the arrangement (see Views) with a made-up song: sections in several meters changing on every track at once, a single extra 2/4 bar, two tracks in meters of their own, and four densities of notes; since milestone 4 its sections are real ones (the extra bar ending the first chorus, and the second chorus named "Chorus 2"), drawn where the markers were, with the two tracks' bars starting again at each section; with `+` (or `=`) and `-` to zoom through seven zoom levels, from a sixteenth note to four whole notes in a column, a quarter note by default. The samples page shows each theme role, the text attributes and the characters the views use. Keys go through the keymap to named commands, with counts as in Vim: `hjkl` and the arrow keys (`cursor-left` and so on), `0` (or Home) and `$` (or End, `{count}$` ending on a later row), `gg` and `G` (`go-first`, `go-last`, or with a count the row or bar counted), `Ctrl-D`/`Ctrl-U` by half a screen and `Ctrl-F`/`Ctrl-B` (or Page Down and Page Up) by a screen less two rows, as Vim does, Ctrl with `hjkl` or the arrow keys to move and scroll with the cursor, so it stays in place on screen until the view can't scroll further (`cursor-left-scroll` and so on, decided in milestone 3; on the arrange page by the current track's bars, the view then starting anywhere in time so the cursor doesn't shift, rather than at a column), `z` to centre the view on the cursor (`scroll-centre`) and `zz` to reset the zoom (`zoom-reset`), which also try out `timeoutlen`, since `z` waits to see if another `z` follows. Escape, or a key with no binding, gives up a count. The cursor stays in the rows and columns fully shown, scrolling only as far as it must, including when the window shrinks. The `:` prompt and the text-size keys work on every page.
- **Editor:** the grammar parser, operators, motions, views and undo history, operating on the song model.
- **The command registry (decided October 2026, built early in milestone 4).** Every action is defined once, in a central registry, before many commands exist. Each entry has a unique name (used on the command line and in config files), a title and short description, aliases for palette search, the views and modes where it applies, its parameters (names, types, defaults and how to ask for them), and its handler; its keys come from the keymap, the defaults from the built-in `modalrc` (decided in milestone 4; see The command registry in use). The keymap and config bindings (`nmap`, `leader`), the hint menu (its labels are titles), the `:` command line and its completion, the palette, macros and `.`, `--write-config`'s list of commands, and a generated command reference all come from it, so a new command appears everywhere at once and none of them can fall out of date. The `:` commands handled specially so far (`set`, the `map` family, `write-config` and the rest) move into it too.
- **Snapshots and sections.** Songs share unchanged sections and tracks between snapshots. Each snapshot also carries its flattened timeline (see Data model), built off the engine thread, which the playback plan is compiled from.

**Planning for in-process plugin hosting**

Hosting VST3/CLAP synths later means an audio engine alongside the MIDI engine. To keep that open from day one:

- The scheduler sends events to *destinations*, not directly to MIDI ports. A destination can be a MIDI port now and a hosted plugin instrument later.
- Plugin hosting would use JUCE's hosting and audio-device modules (ASIO on Windows, ALSA/JACK on Linux, CoreAudio on a Mac), with events delivered sample-accurately in the audio callback.
- Plugin editor windows need native windows next to the SDL3 grid UI; this is workable but needs a spike before committing. The alternative is a JUCE-based window for the whole UI, with the same grid renderer drawn through JUCE.
- JUCE's licence (AGPL or commercial) bears on the undecided licence question.

## Platform specifics

The engine does its own timing on both platforms, so behaviour doesn't depend on OS-level MIDI scheduling. Platform differences stay behind one small MIDI interface.

|  | Linux | Windows |
| --- | --- | --- |
| MIDI API | ALSA sequencer (via libremidi) | WinMM now; Windows MIDI Services where available (via libremidi) |
| Virtual ports | Native: the app creates its own named ports | Not in WinMM: needs loopMIDI or Windows MIDI Services loopback |
| Port sharing | Multi-client | Often single-client under WinMM |
| Engine thread priority | `SCHED_FIFO` via realtime limits (`audio` group or `limits.conf`); no rtkit for now; warns if unavailable | MMCSS "Pro Audio" task |
| Sleeping until next event | Absolute `timerfd` on `CLOCK_MONOTONIC`, polled with an `eventfd` for wakes | High-resolution waitable timer |
| Compiler | GCC / Clang | MSVC |

- **Modal's own ports (decided in milestone 4).** On Linux, Modal creates output ports of its own, which a plugin host or another program connects to like any other port: `ownports` of them (1 by default; 0 for none, up to 16), named `ownportname` (`Modal`), so one is `Modal` and several are `Modal 1`, `Modal 2` and so on, each with 16 channels of its own. Tracks play to them by name like any port (`:port Modal 2`); tracks without a port still play to the `port` setting's, or the first port found, since which port suits is up to each setup. Changing the settings opens new ports at once; ports no longer wanted stay open until Modal restarts, since one the engine may be sending to can't safely be closed. Built after milestone 4. WinMM cannot create ports, so on Windows a virtual cable driver such as loopMIDI does the job, with Modal playing to it by name. vcpkg's libremidi port currently omits the Windows MIDI Services backend; enabling it would need an overlay port. That backend could provide loopback ports, multi-client access and Modal-owned ports on Windows; integration feasibility remains an open question.

- **Clock.** The engine's clock is the steady clock (`CLOCK_MONOTONIC` on Linux, the performance counter on Windows). MIDI input is timestamped on the same clock when it arrives, so recorded and loopback times compare directly with send times. The sleep never wakes early. Before an event, the engine sleeps until a margin before it (1.5 ms by default) and busy-waits the rest, since the first Windows loopback run (October 2026, Babyface, WinMM) showed sleeping alone woke 99% of the time within 0.95 ms, at worst 1.7 ms late. The engine always tells the clock when the next event is due, so the spin starts a margin before it even when that falls inside a routine 1 ms wake-up; a command arriving during a spin waits for it, so commands are seen within the margin rather than 1 ms. With the spin, the engine's own waking on that machine (measured without MIDI) went from 99% within 0.85 ms to 99% within 0.05 ms. The margin is a `--spin` option on the command-line tools, for measuring.
- **Measured timing, Windows.** Loopback runs by Neil, October 2026, on one PC with a Babyface interface through WinMM and a MIDI cable, using `modal-loopback`'s default stream (2,000 notes, one every 10 ms):

  |  | No spin | Spin (1.5 ms) |
  | --- | --- | --- |
  | Latency, due to back: median / p99 / max | 1.46 / 1.95 / 2.38 ms | 1.10 / 1.36 / 1.79 ms |
  | Jitter: p99 − median / standard deviation | 0.49 / 0.21 ms | 0.26 / 0.07 ms |
  | Send lateness: p99 / max | 0.90 / 1.29 ms | 0.35 / 0.54 ms |
  | of which waking: p99 / max | 0.80 / 1.19 ms | within 0.05 / 0.04 ms |

  All messages came back, in order. With the spin, what remains is the driver call (up to about 0.5 ms) and the interface and cable (about 1 ms, mostly the 0.96 ms a 3-byte message takes on the wire). Both are well under the 1 ms threshold for OS-timestamped delivery, so Windows stays engine-timed.
- **Measured recording, Windows.** A `modal-loopback --record` run by Neil, October 2026, on the same setup with the spin, using the default stream at 120 BPM and 960 PPQN (a tick is about 0.52 ms): all 2,000 notes were recorded, none missing or extra, and every one at the tick its arrival time gives. Recorded positions were 1 to 3 ticks late (median 2), which is the loopback latency (median 1.12 ms, max 1.84 ms) rounded down to a tick, and recorded lengths were within one tick of those sent, from rounding each end. A take from a MIDI keyboard through `modal-record` was also checked in the saved file.
- **Measured timing, Linux.** Loopback runs by Neil, October 2026, on a ThinkPad T480 with Ubuntu 26.04.1 (kernel 7.0, a desktop kernel with no real-time tuning) and a Roland UM-ONE, its OUT cabled to its IN, through ALSA, with `modal-loopback`'s default stream (2,000 notes, one every 10 ms) and a Release build:

  |  | Spin (1.5 ms) | No spin | Chords of 3, spin |
  | --- | --- | --- | --- |
  | Latency, due to back: median / p99 / max | 2.12 / 2.26 / 4.61 ms | 2.26 / 2.39 / 4.89 ms | 2.50 / 3.70 / 5.12 ms |
  | Jitter: p99 − median / standard deviation | 0.14 / 0.08 ms | 0.13 / 0.29 ms | 1.20 / 0.82 ms |
  | Send lateness: p99 / max | 0.05 / 0.06 ms | 0.15 / 0.47 ms | 0.05 / 0.47 ms |
  | of which waking: p99 / max | within 0.05 / 0.03 ms | 0.10 / 0.44 ms | 0.05 / 0.47 ms |

  All messages came back, in order. Nearly all the latency is the interface and cable, about 1 ms of it the 3-byte message on the wire and the rest USB and the UM-ONE; Modal's own send lateness is within 0.05 ms for 99% of messages, with an occasional wake about half a millisecond late (under 1% of messages) on this untuned kernel. The chords' larger jitter is the later notes of each chord queuing on the wire, about 1 ms a message, not scheduling. The spin halves waking lateness at p99 (0.05 against 0.10 ms) but changes little at the cable. All of it is well under the 1 ms threshold for OS-timestamped delivery, so Linux stays engine-timed too. The waking row's "within 0.05" above its 0.03 ms maximum was the percentile being reported as its 50 µs step's edge; it is now never more than the maximum.
- **Measured recording, Linux.** A `modal-loopback --record` run by Neil, October 2026, on the same setup with the spin, at 120 BPM and 960 PPQN: all 2,000 notes recorded, none missing or extra, every one at the tick its arrival gives. Recorded positions were 2 to 5 ticks late (median 3, 1.56 ms) against a loopback latency median of 2.03 ms, the arrival rounded down to a tick, and lengths within 1 to 3 ticks of those sent, from rounding each end.
- **Opening ports by name.** A port name given by the user picks out the port with exactly that name, or else the one port with that name ignoring case, or else the one port whose name contains it ignoring case. If several match equally well, or none, the error lists the candidates or all the ports. Ports are opened before playback starts; devices appearing and disappearing during a session come later.
- **SysEx on Windows blocks.** libremidi's WinMM backend waits until a SysEx message has been fully sent, about 0.3 ms per byte at MIDI's speed, and may allocate to copy it. Accepted for milestone 1, since SysEx usually comes at the start of a song. The fix (a SysEx thread per port, keeping later messages to that port behind it, or Windows MIDI Services) stays inside the MIDI backend, behind the scheduler's message sink.
- **Engine thread priority.** `SCHED_FIFO` at priority 70 on Linux; the MMCSS "Pro Audio" task at high priority on Windows. If it can't be raised, the engine runs anyway and says why.

**Build and tooling**

- C++20, CMake, dependencies via vcpkg in manifest mode with a pinned baseline: SDL3, SDL\_ttf (with FreeType, without HarfBuzz), libremidi, Catch2 v3 for tests. Fonts, the built-in `modalrc` and the built-in themes are built into the program from `assets/` by a small CMake step, so it runs with no files installed.
- CI builds and unit tests on both platforms from the first commit.
- **Testing on Linux, in three tiers.** Unit tests run in WSL (Ubuntu 24.04) and in CI with GCC and Clang. ALSA integration tests (ports through `snd-seq-dummy`, notes between virtual ports through libremidi) run on a native Linux install, since neither WSL nor the GitHub-hosted runners have an ALSA sequencer: the runners' Azure kernel ships no sound modules (checked October 2026). A self-hosted runner on that machine could bring them into CI later. Timing is measured only on a native Linux install with real MIDI hardware and a loopback cable.
- A bundled monospace font so the grid looks identical everywhere: JetBrains Mono NL (the version without ligatures), under the SIL Open Font License, shipped with its licence (decided in milestone 3). It has box drawing, shades and eighth blocks, arrows, `♯` and `♭`; it lacks `♮` and the note symbols. Its bold weight is bundled too, for bold text, since synthesised bold looks noticeably cruder. A `font` setting can choose any other.
- A loopback timing test tool: send a steady stream out, receive it back through a cable, report latency and jitter statistics.
- A command-line recorder, `modal-record` (decided in milestone 2): records from an input onto a new track, or merges into an existing one with `--overdub`, optionally playing along with a file, and writes the result as a MIDI file. Its bars come from the play-along file's tempo map and meter, or else from `--tempo` (default 120 BPM) and `--meter` (default 4/4), which can't be combined with a file. Recording is checked through the cable by a `--record` mode of the loopback tool, which reports how far each recorded position is from what was sent. In that mode (decided in milestone 2) the stream is a song at 120 BPM with no metronome or count-in, MIDI thru is off since it would send the stream round the cable again, and the take can be saved with `--save` to look at. It also checks that every note is recorded at the tick its arrival time gives.

**Keeping macOS possible**

macOS isn't planned, but nothing should rule it out. SDL3, libremidi (CoreMIDI) and JUCE all support it, so the rules are:

- No Windows- or Linux-only APIs outside the platform layer; thread priority and timers stay behind the same helpers (macOS would use a Mach time-constraint thread).
- Keymaps treat the main modifier abstractly, so `Ctrl` bindings can map to `Cmd` on a Mac.
- File paths, config locations and fonts go through one small module, not scattered `#ifdef`s.
- CI could add a macOS build early, at low cost, just to keep it compiling.

## Feature notes

- **A menu bar, for those who don't know Vim.** A conventional way in beside the keys: File, Edit, View and Play menus, File holding Open, Save, Export and Exit. SDL3 has no native menus, so it would be drawn on the grid like SPG's own menus or Turbo Vision's, the same on Windows and Linux: opened with a key (F10, say) or the mouse, every item a command from the registry with its keys shown beside it, so the menus can't drift from the keymap. Hideable (`set menubar`) for those who'd rather have the row.

These notes preserve feature descriptions. Their scheduled or someday maybe status is recorded in [schedule.md](schedule.md); inclusion here does not commit an unscheduled feature.

**Finding and developing ideas**
- **Musical search and replace:** `/` searches by interval pattern or rhythm, in any key; `n` jumps between matches; `:s` substitutes across the song.
- **Linked variations:** copies that stay linked to the original, optionally with a transform (inverted, transposed, half speed); editing the original updates every variation.
- **Retrospective capture:** MIDI input is always buffered; one key turns the last few minutes of playing into a take.
- **A notebook (requested November 2026):** a store of musical fragments kept across songs and sessions, outside any song.
  - **Context:** each fragment remembers where and when it came from (the date, the song and section, its key, tempo and meter), and can have a name and tags ("fill", "chorus idea", "7/8 riff").
  - **In:** yank any selection into it or record straight into it. Retrospective capture could also send recent playing there; it is a separate feature, not a dependency.
  - **Out:** a palette prefix searches fragments by name, tag or source song, and auditions them before putting one in; putting can optionally transpose into the current song's key and fit its tempo.
  - **Snippets are the same feature:** a strum pattern or voicing used often is a fragment used often; fields such as key or length make one a template rather than a fixed phrase.
  - **To decide:** where it's stored (in the configuration directory, as a file of its own in the song format, perhaps), how it fits with registers and the paste history, and what fitting a tempo means for a fragment's timing.

**Recording**
- **Half-speed recording:** record at half the tempo (or another fraction) and play back at full speed, for passages too fast to play in; similar uses to step entry.
- **Comping:** combining the best parts of a section's takes (see Sections: looping, takes and count-in).

**Rhythm and time**
- **Polytempo:** a track can run at a ratio of the song tempo (e.g. 3:2) for phasing and tempo canons.
- **Free-time recording:** record without a click, then tap or mark downbeats to fit a tempo map and bar lines.
- **Tuplets and generators:** arbitrary and nested tuplets (7:4, 5:3) as grid settings; Euclidean rhythm transform.
- **Stretch and compress:** a transform that scales a range of bars in time, by a percentage or to a target length in beats or bars.

**Song structure and editing**
- **Linked sections:** "Chorus 2" as a linked instance of "Chorus 1", so editing either changes both, optionally with a transform (transposed, varied); see Linked variations.
- **Song playlist mode:** an ordered list of section references, as an alternative to a strictly linear arrangement.
- **Track loops:** as in SPG, a track can loop (shown by an `L` at its end); a starting point to build on.

**Harmony and arranging**
- **Chord track:** a chord-progression lane used by step entry, transpose-in-key and reharmonisation.
- **Arranging checks:** optional warnings for out-of-range notes per instrument, out-of-key notes, overlapping same-pitch notes, parallel fifths.
- **MusicXML export:** to Dorico, keeping keys and per-staff meters.

**Versions and annotation**
- **Section alternatives:** alternative versions of a section (Chorus A / Chorus B), switchable and auditionable in place.
- **Text lanes:** lyrics, rehearsal notes and cues at song positions.

**Performance and alternative views**
- **Live rig mode:** send program changes and setup messages per song section, stepped through with a footswitch; with a setlist view above the outline view, listing a gig's songs with the same keys, and cue keys per song or section.
- **Tracker view (added October 2026):** the song shown as a tracker shows it, each track a column of rows going down the screen in time, one row a grid step, notes, velocities and controllers written in each row's cells, and played top to bottom. Tracker users like fast, keyboard-driven editing, so Modal could appeal to them; the view would be another way of seeing the same song, beside the piano roll and the event list, sharing their grammar. A large piece of work: to settle then, among other things, how notes off the grid, note lengths and chords fit in rows, and whether patterns map onto sections.
